## 二、PRODUCT-DESIGN.md 评估

### 2.1 优点

1. **边界划分清晰**：§2.2 把"产品提供 vs 用户配置"做成两张表 + 五条边界原则，这是整份方案最有价值的部分，避免了"功能都有但谁负责不清"的常见架构债。
2. **第五原则（配置必须有 UI）是硬约束**：把"用户不用懂 YAML/JSON"上升为产品要求，直接决定了 Phase 4 的工作量，是有意义的产品决策。
3. **五层质量防御体系（§5）设计扎实**：PRE → Agent 自约束 → Gate → Peer Review → POST，每层都标注了产品/用户归属，嵌套结构（项目级 / 任务级 / Agent 内）描述清楚。
4. **成功指标可验证**：§9 给出的指标都带"验证方法"列（如"统计 templates.yaml 中 task_type 数量"），不是空话。

### 2.2 问题与缺口

| # | 问题 | 说明 | 建议 |
|---|------|------|------|
| 1 | "完全达标 ✅"比例偏高 | §1.2 总表称 80% 能力已实现，但细看 §2.4 知识库 70%、边界清晰度 60%，且 §2.7 列出 11 处硬编码债务。"完全达标"项里很多其实是"功能在但边界模糊"，应降级为 🟡 | 在 v1.1 文档里修正等级判定 |
| 2 | 缺少非功能性需求章节 | 性能、并发上限、单项目最大任务数、KB 检索延迟、SSE 连接数上限等均未提及 | 补一节"非功能性指标" |
| 3 | 多 Agent 协作感知被标 🟡 但未给出升级路径 | §3.2 表注"协作上下文较薄（只有名字+角色）"，但 §2.1 仍把它列为已实现能力 | 明确这是设计选择还是缺口 |
| 4 | "自进化"能力被高估 | §6.5 Skill 自进化标 ✅，但 §2.3 自己承认 self_improve_loop 未端到端打通、skill_review 不可观测 | 自进化应整体降级为 🟡 |
| 5 | 路线图（§10）与 UPGRADE 文档的 Phase 划分不完全对齐 | §10 的 v1.1/v1.2/v2.0 与 UPGRADE 的 Phase 0-4 颗粒度不同，读者需要自己映射 | 在两份文档间加交叉引用表 |
| 6 | 未涉及权限/多租户 | 团队级产品通常会问"谁能改 workflow、谁能看成本"，方案完全没有权限模型 | 至少标注为 v2+ 议题 |

### 2.3 设计层面的隐性风险

- **"机制进产品，策略归配置"原则在 Gate 上有张力**：Gate 检查算法是产品能力，但"检查什么章节"归配置。当用户配错 templates.yaml 导致 Gate 永远不通过时，产品该不该兜底？方案未明确。
- **五层质量防御的"Layer 1 Agent 自约束"实际依赖 prompt 纪律**，而 prompt 是用户可配置的（§4.3 prompt_templates.yaml）。这意味着用户可以改 prompt 破坏自约束层——这是配置自由度与质量保证的内在矛盾，方案没有讨论。

## 三、UPGRADE-GAP-ASSESSMENT.md 评估

### 3.1 优点

1. **差距等级 + 优先级双维度**：✅🟡🟠🔴 与 P0/P1/P2 交叉，便于排期。
2. **逐项给出"验证方法"**：Phase 0-4 每个任务都有"改配置为 X 后，验证 Y"的可执行验收语句，符合"可验证性原则"（§8.1）。
3. **三库独立评估矩阵（§3.1）很有价值**：从 Protocol / 存储 / API / 耦合度 / 可测试性五维度对比，结论"偏好库最易独立、KB 需解耦存储、项目库需清理旧路径"与代码实际一致。
4. **配置 UI 缺口的 127 项盘点（§4.1）做得细致**：按类别拆分，P0/P1/P2 分级，并给出后端 API 缺口表，直接可落地。

### 3.2 与代码实际状态的偏差（已核验）

我抽查了若干关键结论，大部分准确，但有需要校正的点：

| 评估结论 | 代码实际 | 校正建议 |

| "store/system_config.py 是配置入口" | 实际入口是 `backend/store/system_config.py`，`backend/base/system_config.py` 是兼容 shim ✓ | §九附录可补精确路径 |
| "agents_registry.json 中 main 的 role=coordinator" | ✓ 准确，但代码层并未读取该 role 字段 | 这正是 Phase 0.1 要补的：让代码从 registry 或 system_config 读 coordinator_id |

### 3.3 工作量估算的风险

| 阶段 | 文档估算 | 评审评估 | 理由 |
|------|----------|----------|------|
| Phase 0 | 5 天 | 5-7 天 | 0.1 协调者配置化涉及 8 个文件 + 测试，1.5 天偏紧 |
| Phase 1 | 7 天 | 8-10 天 | 1.2 存储解耦要定义 MemoryStore Protocol 并迁移实现，2 天偏紧 |
| Phase 2 | 7 天 | 7-9 天 | 2.1 拆 common/ 子目录 + re-export 兼容层是细活 |
| Phase 3 | 10 天 | 10-12 天 | 3.5 自改进闭环端到端打通是最大不确定性 |
| Phase 4 | 12 天 | 12-15 天 | UI 工作量通常被低估，127 项配置全量 UI 是重活 |
| **总计** | **41 天** | **42-53 天** | 文档自己也建议按 1.5x 预估（§7.3），应直接写 55-60 天 |

### 3.4 评估维度的缺口

文档漏了几个值得评估的维度：

1. **测试覆盖度现状未评估**：§8.1 要求"有自动化测试"，但没说当前测试覆盖率多少、哪些路径有测试、哪些没有。重构前应先补关键路径测试，否则"所有现有测试通过"这个验收标准毫无意义。
2. **数据迁移未提及**：Phase 0.6 把 project_service 从 task_data.json 改读 SQLite，但已有的 task_data.json 数据怎么迁移？要不要写一次性迁移脚本？文档没说。
3. **回滚策略缺失**：41 天的大重构，没有任何回滚预案。每个 Phase 应该有"如果失败如何回退"的说明。
4. **并行开发可行性未评估**：5 个 Phase 是否可以部分并行？比如 Phase 4 的 UI 能否和 Phase 2 的结构整理并行？文档按串行写，但实际可能可以压缩。
5. **"向后兼容"与"清理旧路径"的张力未量化**：§8.1 要求向后兼容，但 Phase 0.6 又要删除 task_data.json 旧路径——这两条原则在具体任务上如何取舍，没有判定标准。

### 3.5 Phase 0 验收清单的具体问题

§8.2 Phase 0 验收里有一条：
> "observability_api 的 memory 操作走 KnowledgeBackend 接口"

但 §2.4.1 同时指出 observability_api "直接调 store.memory_*，绕过 KnowledgeBackend 抽象"。这里有个被忽略的问题：**如果 KB 后端是 gbrain（远程），observability_api 走 KnowledgeBackend 后会变慢甚至需要鉴权**。验收标准应补充"切换后端后 API 延迟仍在可接受范围"，否则只是形式上走了抽象层，实际引入性能回归。

### 4.3 验收标准的一致性补强

UPGRADE §8.2 的验收清单与 §8.1 的"可验证性原则"之间存在一处张力：§8.1 要求"向后兼容"，但 Phase 0.6 验收要求"删除所有 task_data.json 后项目列表正常显示"——这实质是破坏兼容。建议在 UPGRADE §8.2 Phase 0 验收清单顶部新增一条判定规则：

```
向后兼容判定规则：
- 凡涉及"删除旧路径"的任务（Phase 0.6），"向后兼容"指旧数据可一次性迁移到新路径，
  迁移完成后旧文件可删除。验收时先跑迁移脚本，再删除旧文件。
- 凡涉及"配置化"的任务（Phase 0.1/0.2/0.3/0.4），"向后兼容"指默认配置下行为与当前完全一致。
  验收时以"默认配置下所有现有测试不变"为安全网。
- 凡涉及"抽象层切换"的任务（Phase 0.5），"向后兼容"指新路径与旧路径在默认后端下行为一致，
  切换非默认后端时允许行为差异但需有性能回归测试。
```

## 五、Phase 0 实施前的修正建议

基于上述评审，Phase 0 开始前应先完成以下文档与流程准备：

- [ ] 在 UPGRADE 新增"测试覆盖现状矩阵"小节

### 5.2 任务排序调整建议

原 Phase 0 顺序为 0.1 → 0.6，建议调整为：

1. **0.6（清理旧 project_service 路径）先行**：它是读路径切换，与其他任务解耦，先做能让后续重构建立在干净的 SQLite 路径上。
2. **0.1（协调者配置化）+ 0.4（显示名统一）合并实施**：两者都涉及 agent_id_policy.py / agent_registry.py，一次性改完成本更低。
3. **0.2（code_project 配置化）+ 0.3（PGD 严格类型配置化）合并实施**：都是 templates.yaml 驱动，改一次配置层即可。
4. **0.5（KB API 走抽象层）与 Phase 1.2（KB 存储解耦）合并到连续工作块**：存储不解耦时走抽象层只是换层调用，意义有限。

### 5.3 每个 P0 任务的"配置开关"规范

为落实 §7.3 缓解措施"引入配置开关，默认值与旧行为一致"，要求每个 P0 任务在实施前明确写清：

| 任务 | 配置开关字段 | 所在文件 | 默认值 | 默认值等价旧行为 |
|------|-------------|---------|--------|-----------------|
| 0.1 协调者配置化 | `system.coordinator_agent_id` | config/system_config.json | `"main"` | 是 |
| 0.2 code_project 配置化 | task_type 的 `outcome_kind` 字段 | business/templates/templates.yaml | 现有 3 个类型置 `outcome_kind: code_project` | 是 |
| 0.3 PGD 严格类型配置化 | task_type 的 `strict_must_include` 字段 | business/templates/templates.yaml | 现有 2 个类型置 `true` | 是 |
| 0.4 显示名统一 | （无开关，直接从 registry 读） | — | — | 是 |
| 0.5 KB API 走抽象层 | （无开关，默认后端 sqlite 行为不变） | — | — | 是 |
| 0.6 旧路径清理 | （无开关，提供一次性迁移脚本） | scripts/migrate_task_data.py | — | 迁移后等价 |

验收时，**"默认配置下所有现有测试不变"是每个 P0 任务的安全网**。

## 六、结论

### 6.1 这两份文档能不能作为升级依据？

**能，但需要先完成 §5.1 的文档修正**。修正后两份文档自洽，且 UPGRADE 的验收标准有测试现状支撑，可以进入实施。

### 6.2 优先级排序是否合理？

**基本合理，建议按 §5.2 调整任务排序**：0.6 先行，0.1+0.4 合并，0.2+0.3 合并，0.5 与 1.2 合并。

### 6.3 最大风险

**不是技术风险，是"边界重构影响现有功能"**。缓解措施见 §5.3——每个 P0 任务必须有明确的配置开关与默认值等价性验证。

### 6.4 总工作量重估

按 §3.3 评估，总工作量应为 **42-53 天**（中位 47 天），按文档自身 §7.3 的 1.5x 原则，建议对外承诺 **55-60 天**。
