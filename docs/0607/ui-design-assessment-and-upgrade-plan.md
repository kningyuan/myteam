# myteam UI 设计评估与升级计划

> 评估日期：2026-06-06
> 评估范围：frontend/（index.html 630 行 + style.css 1531 行 + app.js 3488 行）
> 技术栈：零依赖 Vanilla JS SPA，单文件 CSS 变量主题系统

---

## 一、现状总评

myteam 的 UI 在当前阶段**远超同类工具的平均水准**。作为一个零框架、零构建管线的纯前端应用，它在设计语言一致性、主题系统完备性、暗/亮色模式覆盖、以及毛玻璃质感等视觉细节上已展现出高度审美意识。

### 核心优势

| 维度 | 评价 | 关键证据 |
|------|------|----------|
| 设计令牌体系 | ★★★★☆ | 完备的 CSS 变量系统：三层背景深度、四级文本层级、5 阶圆角、4 层阴影、间距网格 |
| 暗色主题 | ★★★★★ | 深空紫品牌色 + 毛玻璃叠加，质感优于大多数 B 端产品 |
| 亮色主题 | ★★★☆☆ | 功能完整但质感不足，浅色模式下的层次感弱于暗色 |
| 响应式布局 | ★★★★☆ | 3 断点系统（820/700/480），侧栏滑出面板策略合理 |
| 交互流畅度 | ★★★★☆ | CSS transition + spring 动画，悬浮微交互动效完整 |
| 实时体验 | ★★★★☆ | SSE 流式渲染 + 消息渐进式呈现 + 打字指示器 |
| 组件一致性 | ★★☆☆☆ | 无正式组件库，靠约定复用，存在重复/不一致 |
| 代码组织 | ★★☆☆☆ | 单文件 3488 行 JS + 1531 行 CSS，维护成本高 |

### 设计语言定位

当前设计深受 **Arc Browser** 毛玻璃风格影响，品牌色为 **Indigo 紫 (#6366f1)**，选择"深空紫"而非行业惯用的科技蓝，形成独特的视觉识别。这一方向值得保留并深化。

## 二、分模块 UX 审计

### 2.1 导航与布局

**现状**：顶部导航栏 + 左侧栏 + 主内容区三段式。导航含 6 个 tab（Home / Chat / Groups / Projects / Agents / Settings），无二级导航。

**问题**：
1. **信息架构过平**：6 个一级 tab 并列，Projects（可观测性）承载过多子功能（概览 / 执行树 / 交付物 / 成本），全部堆在一个页面内
2. **导航无上下文指示**：当前 tab 下无面包屑或二级导航，深层层级（如项目详情内的子视图）用户易迷失
3. **侧栏信息密度不均**：Chat tab 下左侧栏为 agent 列表，Groups 下为 group 列表，Projects 下为空——同一物理位置承载不同语义，缺乏一致性

**建议**：
- 引入二级导航（侧栏内分段 tab）来组织深层层级
- Projects 页引入面包屑：`Projects > {project_name} > Execution`
- 统一侧栏语义：左侧始终为"资源列表"，右侧始终为"详情/主内容"

### 2.2 仪表盘 (Home)

**现状**：顶部 4 个统计卡片（Projects / Running / Tokens / Cost）+ 项目网格卡片。

**问题**：
1. **统计卡片信息量过低**：4 张卡片只显示数字 + 标签，无趋势/对比/时间维度
2. **项目卡片样式不一致**：`.stat-card` 与 `.home-card` 使用不同圆角和阴影
3. **空态缺失**：首次使用无项目时，项目网格区域为空白，无引导提示

**建议**：
- 统计卡片增加趋势微标（↑↓）或迷你 sparkline 图
- 统一卡片设计语言
- 空态增加创建项目引导 + 示意图/文案例

### 2.3 聊天界面 (Chat)

**现状**：左侧 agent 列表 → 选中后中间聊天区域 → 底部输入框。支持流式渲染、thinking 块折叠、引用卡片。

**问题**：
1. **消息信息层级扁平**：用户消息 vs Agent 消息 vs 系统消息的视觉区分不足，主要依赖颜色而非布局结构差异化
2. **Thinking 区域折叠体验生硬**：点击展开/折叠整个 thinking 块，缺少渐进式展开或行内锚点
3. **引用卡片空间效率低**：`.citation-card` 占据完整消息宽度，多条引用时阅读流断裂
4. **长消息性能**：3488 行 JS 中的 `renderAgentMsg` 使用 `innerHTML` 全量替换，极端长消息（>10 万字）可能导致明显卡顿
5. **多轮对话的上下文视觉缺失**：无法一目了然看出当前第几轮、token 消耗趋势

**建议**：
- 设计清晰的"三栏"消息结构：角色标识（头像/色带）+ 时间戳 + 内容，而非仅靠颜色区分
- Thinking 区改为带行号锚点的可折叠区，支持"跳转到第 N 个 thinking 块"
- 引用卡片改为紧凑行内式（类似 GitHub 引用）
- 引入虚拟滚动（virtual scroll）或分页加载长对话
- 对话轮次增加分割线 + 轮次摘要（token 数、耗时）

### 2.4 群组聊天 (Groups)

**现状**：支持 @mention 分配消息到特定 agent，侧栏显示群组成员。

**问题**：
1. **@mention 无补全列表 UI**：用户需手动输入 `@` 后等待文本匹配，无可见候选列表
2. **群组消息流与单人聊天视觉同质化**：同一组件复用，但群聊需要更清晰的"发言人"标识
3. **群组配置入口深**：需先选中 group 再找配置按钮

**建议**：
- 增加 `@mention` 下拉候选面板（类似 Slack/Discord）
- 群聊消息增加发言人头像 + 姓名色带
- 侧栏 group 卡片增加快捷设置入口

### 2.5 可观测性 (Projects)

**现状**：4 个子标签页——Overview（DAG / Fleet 状态 / 成本）、Execution（交互树，实时 SSE 更新）、Deliverables（文件树 + 预览面板）、Cost（Token/预算明细）。

**这是全应用功能最重、信息密度最高的模块**，也是当前 UI 挑战最大的部分。

**问题**：
1. **DAG 可视化缺失**：Overview 中的任务 DAG 以列表形式呈现，无图形化拓扑图——这恰恰是协作引擎的核心卖点
2. **执行树（execution tree）可读性差**：交互以简单缩进列表展现，层级深时难以跟踪
3. **实时更新无视觉提示**：SSE 推送新事件时仅追加内容，无高亮/闪光动画告知用户"有新数据来了"
4. **交付物预览与编辑分离**：文件树选中后右侧只读预览，无法在同一上下文进行编辑或对比
5. **成本可视化薄弱**：Cost tab 以表格展示，无图表（柱状图/饼图）直观呈现 token 分布

**建议**：
- **引入 DAG 图组件**：使用 Canvas/SVG 呈现任务依赖拓扑，节点着色反映状态（完成/运行/失败/跳过）
- 执行树增加"紧凑/展开"切换模式，支持按状态过滤
- 实时更新增加微高亮动画（淡黄色闪光持续 2s）
- 交付物增加"分栏对比"模式：源文件 vs 渲染效果
- Cost 页增加柱状图 + 饼图可视化（可用纯 CSS/SVG 实现，无需第三方库）

### 2.6 Agent 管理 & 设置

**现状**：表格展示 agent 列表 + 内联编辑 + 只读任务类型注册表。

**问题**：
1. **表格列过多，水平滚动频繁**：Agent 表含 7+ 列，在 <=1280px 视口下几乎必然溢出
2. **内联编辑缺少确认反馈**：点击编辑后直接修改值，无"保存/取消"按钮，误操作无撤销
3. **设置页面密度失衡**：部分卡片只有 1-2 个字段，大部分空间空白

**建议**：
- Agent 表增加列定制/隐藏能力，关键信息（状态/模型）固定前置
- 内联编辑改为点击后出现确认/取消按钮，或使用双击编辑模式
- 设置页改为分组折叠式（Accordion），减少一次性信息暴露

## 三、设计系统升级

### 3.1 当前设计令牌的 gaps

| 缺失项 | 必要性 | 建议 |
|--------|--------|------|
| `--space-0` (0px) | 低 | 补齐即可，可用于重置 margin |
| `--space-7/9/10/11` (28/36/40/44px) | 中 | 4px 网格不应跳过中间值，设计中对 28px 间距有实际需求 |
| `--text-4xl/5xl` (36/48px) | 低 | 品牌展示（logo/空态插图用） |
| `--font-weight-medium/semibold/bold` (500/600/700) | **高** | 当前直接使用 `font-weight: 600`，分散在各处 |
| `--z-index` 层级系统 | **高** | 无管理，可能导致 modal 被 sidebar 或 toast 遮挡 |
| `--line-height` 系统 | 中 | 当前行高分散定义，影响排版一致性 |
| `--opacity` 层级 (disabled/hover/active) | 中 | 多处使用 opacity 值散落 |
| 动画缓动命名规范化 | 低 | 3 种 transition + 1 种 spring，建议扩展至 5-6 种 |

### 3.2 组件库建议

建立正式的内部"设计原子"系统，定义以下组件：

**基础原子**
- Button（6 变体：primary / secondary / ghost / danger / icon / link）
- Input（text / textarea / select / search）  
- Badge / Tag / Chip
- Tooltip
- Toast / Notification
- Modal / Drawer
- Spinner / Skeleton

**复合分子**
- Card（stat / project / agent / group / citation）
- Table（sortable / filterable / in-line editable）
- Tab（一级 / 二级 / 胶囊）
- Message Bubble（user / agent / system / thinking）
- Tree View（DAG / file tree / interaction tree）
- Empty State（带插图 + 引导文字）

**组织模板**
- Page Layout（nav + sidebar + content + optional detail panel）
- Form Section（grouped fields with validation state）
- Data Dashboard（stat row + chart + list）

### 3.3 亮色主题改进

当前亮色主题是最大短板：
- 背景对比度偏低，`--bg-base` 与 `--bg-elevated` 差异不足 5%
- 毛玻璃效果在浅色背景下几乎不可见
- 品牌色 (#6366f1) 在白色背景上缺乏冲击力

**建议重构亮色方案**：
- 采用暖白基调（#f8f9fa → #ffffff），增加背景层次
- 毛玻璃在浅色模式改用半透明白 + 细微阴影，而非 blur
- 品牌色使用更饱和的 indigo (#4f46e5) 作为浅色模式的主色

## 四、工程架构升级

### 4.1 CSS 架构

| 问题 | 影响 | 建议 |
|------|------|------|
| 单文件 1531 行 | 维护困难，命名冲突风险 | 拆分为：`tokens.css` / `layout.css` / `components.css` / `pages.css` |
| 选择器特异性混乱 | 部分 ID 选择器与 class 覆盖冲突 | 统一使用 class 选择器，保留 ID 仅用于 JS 钩子 |
| 重复/重叠样式块 | `.chat-actions` 定义 2 次，`.deliverable-body` 定义 3+ 次 | 清理冗余，确认后合并 |
| 未使用的设计变量 | `--mono`、`--accent`、`--bg-secondary` 出现但未定义 | 迁移到正式 token 体系后移除 |
| `-webkit-` 私有前缀 | 仅覆盖 Chrome/Safari，Firefox 降级 | ✓ backdrop-filter 已有标准；scrollbar 可保留 webkit-only（Firefox 滚动条本身可接受） |

### 4.2 JS 架构（UI 层面）

**核心问题**：`app.js` 3488 行单体，无模块化、无组件生命周期、DOM 渲染全量重建。

**短期建议**（不改框架前提下）：
1. 按功能拆分为 5-6 个文件（`chat.js` / `projects.js` / `agents.js` / `groups.js` / `settings.js` / `ui-core.js`），通过 `index.html` 的 `<script>` 标签加载
2. 引入简单渲染函数模式：`renderComponent(props) => string/htmlElement`，替代全局 `innerHTML`
3. 事件绑定改用委托模式（delegation），减少 `setupEventListeners` 中 350 行的逐一绑定

**长期建议**：
- 评估迁移到轻量框架（如 Preact / Lit / Svelte）的成本收益。受益：组件化、虚拟 DOM diff、开发体验。成本：需要构建工具链、学习曲线、现有代码重写量
- 或采用 **Web Components** 方案，渐进式替换，不引入构建工具

## 六、设计原则（追加到现有原则）

现有 CLAUDE.md 中的原则已较完善，建议补充：

1. **渐进式披露（Progressive Disclosure）** — 不要一次性展示所有信息。可观测性等复杂页面默认展示摘要，允许用户按需深入
2. **状态可见性（Status Visibility）** — 每个操作都应产生可见反馈。一是实时操作（加载态、成功/失败态），二是持久状态（系统当前配置、任务当前阶段）
3. **容错设计（Forgiving Design）** — 误操作应可逆或可确认。内联编辑应有保存/取消、删除操作应有二次确认、配置修改应有"应用/重置"模式
4. **空态不是空白态** — 没有内容 ≠ 显示空白区域。空列表应引导用户进行下一步操作，空结果应提示修改搜索/筛选条件

## 八、总结

myteam 的 UI 现有基础**远高于同类工具的 typical 水准**——设计令牌体系完整、暗色主题质感出色、实时交互体验扎实。但受限于单体架构、零组件抽象、以及信息架构随功能增长自然膨胀的现状，已接近"单文件维护"的极限。

**核心里程碑**：

1. **短期**—亮色主题翻新 + 空态体验补全 + @mention 直接可见
2. **中期**—消息结构升级 + 执行树可读性 + 成本可视化
3. **长期**—DAG 图 + CSS/JS 模块化 + 可选的 Web Components 迁移

> 最重要的一个设计决策：在引入 DAG 图之前，当前的 Projects 页面缺少**对协作引擎核心价值的可视化表达**——这是 UI 与产品价值之间最大的 gap。
