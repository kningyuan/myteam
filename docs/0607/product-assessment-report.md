## 1. 执行结论

**架构成熟度：4.5/5 — 产品完整度：3.0/5 — 用户体验：2.5/5**

最核心的结论：myteam 的编排内核已经是一项**可量产的资产**，但整个项目卡在「可运行的框架 → 好用的产品」的过渡期。对未来最大的风险不是技术债，而是**产品化不足导致落地案例不足，从而得不到足够的真实反馈来迭代**。

**行动建议**：接下来 1-2 个迭代集中解决「新用户 5 分钟内跑通并理解发生了什么」和「交付物可见」两个问题，把体验门槛从小时级降到分钟级，换取第一批真实用户的使用反馈。

## 3. 架构亮点（已确认落地，应视为核心资产保护）

### 3.1 三层边界模型完全落地

> System Kernel / Strategy Registry / Skill Pack 三层分离不是纸面设计。

`process.py` 从 979 行重构到 ~282 行，拆出了 `plan_gate`、`task_pipeline`、`decision_pipeline`、`dag_dispatch`、`plan_expansion`、`plan_splice` 六个独立模块。每一个模块有明确的职责边界和可独立测试的接口。

```
decision_pipeline (team_config / task_plan / evaluate / triage)
       ↕ plan_expander
task_pipeline (execute → gate → quality → peer_review)
       ↕ settle / retry / triage
process (状态机 + 调度)
```

每个模块的构造函数在 100 行以内(不含测试)，符合单一职责原则。

### 3.2 Plan Gate 确定性约束体系

`plan_gate.py` 是「流程约束 agent 成果」的核心机制，涵盖了：
- Kahn 拓扑排序检测 DAG 环
- agent 能力边界校验（`agent_task_type_map()`）
- task_type 注册表存在性校验
- 扇出（fan-out）上限控制
- 在 task_plan retry 循环中执行——plan 被拒后 agent 收到明确反馈并重试

这套机制的设计质量业界领先，优于多数编排框架的「通过了再说」的做法。

### 3.3 契约驱动的 Interaction 设计

`InteractionRequest` / `InteractionResponse` 作为**唯一的**跨层数据合约，使用 Pydantic 判别联合体（discriminated union）按 `kind` 区分 6 种交互类型。每种 kind 的 response 经过 submit_result 本地验证后才写入。没有 JSON「修复」/「抢救」路径——拒绝无效输出，不做模糊容忍。

这保证了系统边界的**确定性**，是编排系统最难的工程问题之一，myteam 给出了正确的答案。

### 3.4 断点续跑与崩溃恢复

`task_pipeline.settle_in_progress_task()` + `agent_port` 中的残骸回收逻辑考虑到了：
- 进程级崩溃后的 workspace 残骸清理
- 部分完成的 task 重新入队
- token 计量和 budget 边界检查

多数编排框架在这点上是缺失的。「能跑」和「崩溃后能恢复」之间差了一个工业化程度。

## 4. 当前短板（按优先级排列）

### P0：从「跑通」到「看懂发生了什么」的断层

| 问题 | 具体表现 |
|------|----------|
| 命令行输出过于技术化 | `run_kernel.py` 的输出以日志级别为主，缺少面向用户的进度展示 |
| 无可观测 UI 配套 | observability API 存在但 Hub 前端没有消费它来做项目级看板 |
| 失败原因不可理解 | 错误消息是代码级的 Exception 堆栈，没有翻译成用户可操作的语言 |
| 交付物不可浏览 | 产物散落在 `business/tasks/project/<id>/deliverables/` 目录下，没有聚合展示 |

**影响**：这是目前最大的产品断层。如果用户跑完一个项目后无法直观地看到「发生了什么、得到了什么」，那么编排引擎再强大也无法转化为用户价值。

### P1：新用户从零到跑通的路径过长

当前新用户需要：
1. 克隆代码 → 2. 配置 venv → 3. 安装 opencode CLI → 4. 阅读架构文档 → 5. 手动创建 project_config → 6. 手动配置 agents_config → 7. 配置 workspace → 8. 运行 kernel → 9. 失败后读源码排查

这个链条上有 5 个以上的摩擦点。在缺乏用户文档的情况下，新用户预期需要 30-60 分钟才能跑通第一个项目。

### P2：单项目可观测性

当前 Hub 的 observability 页面（`observability_api.py`）提供了原始数据的读取能力，但：
- 没有项目级别的进度可视化（当前正在执行哪个 task、完成了多少）
- 没有 deliverable 列表和内容预览
- 没有 task DAG 的图形化展示
- 没有历史运行记录对比

**这是一个产品缺口，不是功能缺口**——API 层已经提供了所需数据，只缺前端消费。

### P3：非功能性短板

| 维度 | 当前状态 | 建议目标 |
|------|----------|----------|
| 安全性 | Hub 绑定 0.0.0.0，无鉴权，无 CORS | 至少加简单 API key 鉴权和 CORS 白名单 |
| 错误消息 | Python 异常堆栈直接暴露给用户 | 面向用户的错误代码 + 操作建议 |
| 配置验证 | 运行时才能发现配置错误 | 启动时做配置 Schema 校验 |
| 前端工程 | app.js 单文件 > 3500 行，无测试 | 模块拆分 + 关键交互测试 |

### P4：业务配置的可发现性

注册表 API（`hub/services/agent_registry.py`）在 2c0a7b4 已添加，这是正确的方向。但：
- 目前只有 task_type 和 agent 约束查询
- 缺少对 templates.yaml 中所有可用 task_type 的能力卡片展示
- 缺少对 agent 角色与 skill 映射关系的可视化管理

## 5. 竞品对标分析

### 5.1 AutoGen（Microsoft）

| 维度 | AutoGen | myteam |
|------|---------|--------|
| 抽象层次 | 代码级 API，用户写 Python 编排 | 声明式 goal → DAG 自动分解 |
| 约束机制 | 基于代码逻辑，无确定性门禁 | Plan Gate + 契约验证 + 注册表约束 |
| 可观测性 | 依赖外部工具集成 | 内建 SQLite 真相库 + Observability API |
| 上手成本 | 低（pip install 即可） | 高（需要完整环境配置） |
| 社区生态 | 丰富的示例和文档 | 几乎为零 |

**差异点理解**：AutoGen 走的是「给开发者一个灵活框架」路线，myteam 走的是「给业务流程一个确定性约束」路线。两者的目标用户不同，myteam 的差异化优势在编排质量上，不是在上手速度上——但当前的上手成本已经高到了**掩盖差异化优势**的程度。

### 5.2 CrewAI

| 维度 | CrewAI | myteam |
|------|--------|--------|
| 编排模型 | 线性 Pipeline + 层级管理 | DAG + 确定性门禁 |
| 任务分解 | 用户手动定义 task | 自动 goal → DAG 分解 |
| 失败处理 | 简单重试 | Gate 校验 + 降级 + triage |
| 配置复杂度 | 低（Pythonic API） | 高（多文件配置） |

### 5.3 LangGraph

LangGraph 更强调图的灵活性和 agent 自主性，myteam 更强调约束和可控性。这不构成直接竞争——两者的关注点不同。但如果用户追求「快速搭一个 agent 协作流程」，LangGraph 的示例和文档丰富度远超 myteam。

### 5.4 竞品启示

1. **文档就是产品**：上述竞品都有高质量的文档和示例，这是它们的第一入口。myteam 当前没有用户侧文档。
2. **demo 就是最好的营销**：一个 5 分钟能跑的 demo 项目，价值超过十页架构说明。
3. **差异化在于确定性和门禁**：这是竞品没有做到的，是 myteam 的核心卖点。产品化应当强化这个认知。

## 6. 分阶段改进建议

### Phase A（立即开始，1-2 周）

| 编号 | 改进项 | 工作量 | 预期效果 |
|------|--------|--------|----------|
| A1 | 提供 demo 项目模板 + 一键启动脚本 | 小 | 新用户 5 分钟跑通 |
| A2 | 用户侧 Quick Start 文档 + 故障排查指南 | 小 | 新用户自助成功率 > 60% |
| A3 | 改进 CLI 输出：进度条 + 当前步骤说明 + 完成摘要 | 中 | 运行过程可理解 |
| A4 | 前端交付物面板（读取 deliverables/ 目录展示） | 中 | 交付物可见 |

具体说明：

**A1 demo 项目模板**
- 预配置一个 `hello_demo` 项目，包含完整的 `project_config.json`、`agents_config.json`、workspace 初始结构
- 在 `run.sh` 中加 `--demo` 参数：一键完成配置初始化 → 运行 → 输出结果

**A2 用户文档**
- `docs/quick-start.md`：5 步指南，每一步对应一个可执行的命令
- `docs/troubleshooting.md`：常见错误 + 原因 + 解决方案对照表
- 已有的架构文档保留为「进阶阅读」，不作为新用户的第一站

**A3 CLI 输出改进**
- 在 `run_kernel.py` 的输出中加入进度指示框架
- 区分「信息日志」（开发者看）和「用户进度」（用户看）两个 channel
- 项目结束时输出格式化的完成摘要：task 数量、完成/失败/跳过、总耗时、交付物列表

**A4 交付物面板**
- 利用已有的 observability API，在 Hub 前端添加一个项目交付物浏览页
- 展示：项目列表 → 单项目 task DAG → task 详情 → 交付物预览
- 当前数据层已有，只需要前端消费

### Phase B（紧随其后，2-4 周）

| B2 | 配置错误的面向前端校验 | 中 | 配置错误在启动时被发现 |
| B3 | 基础 API 鉴权 | 小 | 面向安全的外网演示 |
| B4 | 多项目运行历史管理 | 中 | 可回溯比较 |

### Phase C（远期规划）

| 编号 | 改进项 | 优先级 | 说明 |
|------|--------|--------|------|
| C1 | team_config 的 Web UI 编辑器 | 中 | 降低非技术用户的配置门槛 |
| C2 | task_type 注册表的管理界面 | 低 | 让策略人员可自助修改 |

## 7. 不确定性声明

以下事项需要进一步验证，在当前报告中标注为「假设」：

1. **目标用户假设**：本报告假设 myteam 的核心用户是有一定技术背景的团队管理者或独立开发者。如果实际用户是纯业务人员，上述建议中与 CLI/配置文件相关的内容优先级需要下调，Web UI 编辑器的优先级需要上调。
2. **竞品信息时效性**：AutoGen/CrewAI/LangGraph 的产品状态以 2026 年 6 月的公开信息为准，可能已有变化。
3. **没有一手用户反馈**：当前评估基于代码阅读和架构分析，缺少真实用户的意见。上述改进建议的优先级应在获取首批用户反馈后重新校准。
4. **工作量估算为粗略估计**：A1–A4、B1–B4 的工作量标签（小/中）相对而非绝对，需要研发团队评估后确认。
