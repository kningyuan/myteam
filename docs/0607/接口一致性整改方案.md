## 0. 一句话背景

逐一映射了 50 个前端调用点到后端路由：**路径 / 方法 / 请求体 / SSE 事件名全部对齐**。问题集中在**响应字段**与**运行态语义**上，共 4 个（B 为纯前端 bug，A/C/D 在后端，E 为跨端约定）。

**关键判断**：这不是简单的"前端 vs 后端"分歧，而是 **代码 / 契约文档(`api-reference.md`) / 前端** 三方漂移。例如：

- `api-reference.md:790` 明确写 `/overview` 返回 `title`，前端也读 `title`——**只有代码没返回**（A）。
- `api-reference.md` 附录 B 声明"所有核心项目/状态 API 使用统一错误格式 `{error:{...}}`"——**但代码一半端点抛 `HTTPException` 返回 `{detail}`，前端又主要读 `detail`**（E）。

所以整改原则是：**以 `api-reference.md` 为唯一契约源，让代码与前端都回归契约，并加测试把三方钉死。**

### D. 收口"运行态三源不对账"

> **架构定性**：D13 定 SQLite 为唯一真相，而当前运行态三源并存——这是对 D13 的实质违背。D-fast 治标、D-proper 回归 D13，方案选型见「评审说明 Q1」。

**事实**（已取证）：
- `_KERNEL_RUNS` 的功能性读写仅存在于 `server.py`（`run_kernel.py` 零引用；`job_supervisor.py:1` 仅模块 docstring 提及「替代 `_KERNEL_RUNS` 内存 dict」，非功能引用）。

- `/api/projects/run-status`（`server.py:954`）只读 `_KERNEL_RUNS` → 重启续跑期间恒报 `running:false`。
- 续跑端点（`server.py:963-966`）两道守卫此时全部放行 → 可与启动线程并发跑同一 DAG（仅靠内核 reconcile 兜底）。
- `JobSupervisor.start_job` **全代码库零调用**——`_KERNEL_RUNS → job 表`的迁移是半成品，`resume_orphans()` 永远扫不到东西。

#### D-fast（本批，推荐）—— 让自动续跑期间 `_KERNEL_RUNS` 反映真实运行态

思路：给内核函数加一对**中性回调**（不引入 hub 依赖，遵守分层），由 hub 注入"标记/清除 `_KERNEL_RUNS`"。

**文件 1**：`backend/common/run_kernel.py` `resume_in_progress_projects()`

```python
def resume_in_progress_projects(*, store=None, backend=None,
                                on_start=None, on_end=None) -> list[str]:
    store = store or Store()
    reconcile_on_start(store)
    gc_workspace(store)
    resumed: list[str] = []
    for proj in store.list_projects():
        pid = proj["project_id"]
        if proj.get("status") not in ("in_progress", "paused"):
            continue
        if on_start:                      # ← hub 注入：标记 running
            on_start(pid)
        try:
            resume_project(pid, store=store, backend=backend)
            resumed.append(pid)
            if on_end: on_end(pid, None)  # ← 清除
        except Exception as e:
            if on_end: on_end(pid, e)
            continue
    return resumed
```

**文件 2**：`backend/hub/api/server.py` `_auto_resume_on_startup()`

```python
def _mark_run(pid):
    _KERNEL_RUNS[pid] = {"running": True, "error": None}
def _clear_run(pid, err):
    _KERNEL_RUNS[pid] = {"running": False, "error": str(err) if err else None}

resumed = resume_in_progress_projects(on_start=_mark_run, on_end=_clear_run)
```

效果：续跑期间 `run-status` 正确返回 `running:true` → 前端续跑按钮正确隐藏（`project.js:129` 的 `resumable` 判定）→ 续跑端点守卫 `_KERNEL_RUNS[pid].running` 生效，堵住并发续跑窗口。

> 【待后端确认】是否接受"回调注入"方案；或后端更偏好在 hub 层自行遍历 in-progress 项目（不改内核签名）。两者都能达标，回调方案分层更干净。

```python
async def http_exception_envelope(request: Request, exc: HTTPException):
    return JSONResponse(status_code=exc.status_code, content={
        "error": {"code": f"HTTP_{exc.status_code}", "message": exc.detail,
                  "hint": "", "doc_url": ""},
        "detail": exc.detail,   # 向后兼容：旧前端仍读 detail
    })
```

## 4. 接口契约与防复发机制（双方共识 —— 本方案核心）

只修 bug 不立机制，下次还会漂。约定如下四条：

### 4.1 单一契约源
`docs/api-reference.md`（"前端消费视角"）定为前后端**唯一接口契约**。本次问题本质是 **代码 / 契约 / 前端三方漂移**；整改后三者必须一致。本批同时勘误契约文档自身的漂移点（如 overview 示例里多写的 `created_at/updated_at`、少写的 `budget_ratio/budget_state`），以**前端实际消费字段**为准对齐。

### 4.2 统一错误信封（落实附录 B）

### 4.4 后端响应形状测试（防回归的硬约束）
新增 `backend/common/tests/test_api_contract.py`，对**前端实际消费**的关键端点断言响应必含字段——字段被删/改名 → CI 立刻红：
