## 二、Cursor Subagent 协作 vs myteam 内核编排：能力对照表

> 本节基于 handoff §1.2 确认的事实：本轮改动是 **Cursor Task subagent**（IDE 侧），不是 `run_kernel.py` 驱动的 workspace agent。

| 协作维度 | Cursor Subagent（本轮实测） | myteam 内核编排 | 差距方向 |
|---------|--------------------------|----------------|---------|
| **任务派发** | 用户一句话 → Cursor 自动分解为子任务 → 并行执行 | `run_kernel.py` + workflow YAML 声明 DAG → 顺序/静态执行 | myteam 缺**动态拆解**；优势是**确定性 DAG + Gate** |
| **并行** | IDE 内多 workspace tab 真并行（四路调查 handoff §1.3） | DAG 依赖图支持并行声明，但 Process 顺序调度（D12 未落地） | myteam 并行在计划未在代码 |
| **handoff / 上下文传递** | 通过 `/tmp/handoff-*.md` 人工写入下一 session；session 内上下文自动 | Gate retry 传旧稿路径（P1 已落）；跨任务 handoff 靠 deliverable 文件 | myteam handoff 粒度更粗，无结构化 context bundle |
| **交叉验证** | 四路 workspace 独立调查 → 人工汇总发现矛盾 | decision-record 仲裁节点（main agent 汇总多路 review） | myteam 有**制度化交叉验证**，但依赖 main agent 能力 |
| **session 续聊** | Cursor 对话天然有上下文窗口；切换 session 丢失 | Hub 聊天有 `SessionStore`；内核 execute **无 session**，每次新 interaction_id | 内核编排缺 session；Hub 聊天已有 |
| **动态拆任务** | Cursor 按复杂度自动追加子任务 | `PlanExpander` 仅在派发前静态展开；超时走 failed | 内核缺**运行时再拆**能力 |
| **角色/身份注入** | Cursor rules（alwaysApply）自动注入；每次会话全量 | Hub 聊天通过 `_merge_rules`；内核 execute 不读 AGENTS.md | 内核编排角色漂移，Hub 聊天已对齐 |
| **错误恢复** | 用户在 IDE 重试，上下文保留 | `task_pipeline` P1 已附旧稿 retry；Gate 3 次后 triage | 内核有**制度化 triage**，Cursor 靠人工干预 |
| **可观测性** | Cursor 对话历史；无 DAG 图 | Obs API + SQLite 全量持久化；R3 计划 DAG 图 | myteam 优势：**可持久查询**；劣势：当前 UI 弱 |
| **外部工具调用** | MCP（browser, gbrain 等），tool 生态丰富 | 纯 CLI subprocess（opencode/claude）；无 tool 注入机制 | myteam 缺**工具调用扩展点** |
| **成本管控** | 无 budget 上限 | `budget` 字段 + 超预算停止 | myteam 优势 |
| **部署/运行时** | IDE 进程内，无持久化 | SQLite 持久化；崩溃可续跑 | myteam 优势 |

### 核心结论

```
Cursor Subagent 优势：动态拆解、真并行、丰富工具生态、零配置上手
myteam 内核优势：确定性 DAG + Gate、持久化、成本管控、交叉验证制度化、可审计
```

两者不是替代关系——**Cursor 适合探索性、快速迭代任务；myteam 适合需要可审计、可回滚、多角色协作的工业化任务**。

## 四、三个阶梯式验证项目

每个验证项目是一个真实的 `run_kernel.py` 任务，跑通则证明框架升了一个等级。设计原则：**最简 goal、最短 DAG、每关明确 pass/fail 标准**。

---

### Level 1：「单角色 Gate 首次通过率 ≥ 80%」

**验证目标**：内核 P0/P1 修复（rules 注入 + prompt/Gate 同源）后，角色首次交付即通过 Gate 的比例。

```yaml
项目 ID: gate-pass-rate-l1
workflow: hotfix  # 最短路径
goal: >
  研究并撰写一份《myteam Gate 校验机制说明》（500字以上），
  覆盖：调研背景、关键发现、结论、风险评估
mode: one_shot
budget: 20000
agents: [research]   # 单角色
task_type: research  # 有明确 check_rules
```

**Pass 标准**：
- `research-report` 任务 `gate_retries = 0`（一次通过）且 `status = completed`
- `pytest backend/common/tests/test_agent_transport.py` 全绿
- 查 SQLite：`SELECT gate_retries, status FROM tasks WHERE task_id='research-report'`

**当前预测**：rules 未注入时约 40-50% 首次通过；P0 rules 注入后目标 ≥ 80%。

**升级证明**：Level 1 通过 = 能力 #2（角色身份注入）已生效。

---

### Level 2：「三角色并行评审 + decision-record 闸门端到端」

**验证目标**：software-delivery / hotfix 的 requirements 阶段（三路并行 review + main 仲裁）全流程跑通，决策阶段开放 🔴 = 0。

```yaml
项目 ID: three-way-review-l2
workflow: hotfix
goal: >
  修复 myteam Hub 设置 Tab 与内核配置断层问题：
  skill_config.process_defaults 应传入 ProcessConfig/WatchdogConfig。
  需求范围限于 backend/hub/api/server.py 与 backend/common/run_kernel.py。
mode: one_shot
budget: 80000
agents: [product, arch, qa, main]
```

**Pass 标准**：
- 全部 9 个任务 `status = completed`
- `req-decision` 交付物中 `开放 🔴：0` 文本存在（Gate `must_include` 校验）
- 总用时 < 30 分钟（含 Gate retry）
- 无 `triage` 任务触发

**升级证明**：Level 2 通过 = 能力 #1（确定性编排）+ #2（角色）+ #6（交付物闭环）三项协同工作。

---

### Level 3：「内容→发布→证据验证」全链路（场景 B/C 最小 E2E）

**验证目标**：content-campaign workflow 从调研到发布全流程跑通，`publish-post` 任务的证据 URL 可访问。

```yaml
项目 ID: content-publish-l3
workflow: content-campaign
goal: >
  生产并发布一篇关于「myteam 多 Agent 协作原理」的知乎专栏文章（800字以上），
  关键词：多Agent编排、任务拆解、Gate校验。附发布后 URL 和截图证据。
mode: one_shot
budget: 60000
agents: [main, product, research, content]
```

**Pass 标准**：
- `publish` 任务交付物中 `已发布URL` 字段包含 `https://`
- Gate `evidence_url.url_must_match` 校验通过（或同等平台规则）
- `acceptance` 验收报告 `发布建议` 为「建议发布」或「可合入」
- 跑完无需人工干预

**升级证明**：Level 3 通过 = 框架支持**外部侧效动作 + 证据验收**，即场景 B/C 最小商业闭环。

---

### 阶梯关系

```
Level 1（单角色 Gate）
    ↓ 解锁
Level 2（多角色并行 + 仲裁）
    ↓ 解锁
Level 3（内容发布 + 外部证据）
    ↓ 解锁
Level 4（浏览器自动化 + 效果采集）  ← 当前框架需扩展能力才可达
Level 5（运行时动态拆分 + 跨 cycle 记忆）
```

## 五、升级治理机制：防止「东搞一下西搞一下」

### 5.1 核心问题诊断

当前症状：
- 多会话分头改 `agent_transport.py` / `task_pipeline.py` / `server.py`，无 invariant 守护
- handoff 文档靠人写，格式不统一，接续 session 信息不完整
- P0/P1 改动未 commit，无法回归
- 没有统一指标（Gate 首次通过率、任务完成时间 p95、token 利用率）

### 5.2 版本门控机制

**原则：只有通过对应 Level 验证项目，才允许推进该里程碑的代码合入。**

```
┌─────────────────────────────────────────────────────────┐
│                  升级门控流程                            │
│                                                         │
│  代码改动（feature branch）                             │
│       │                                                 │
│       ▼                                                 │
│  运行回归项目集（见 5.3）── FAIL ──→ 不得合入           │
│       │ PASS                                            │
│       ▼                                                 │
│  运行对应 Level 验证项目 ─── FAIL ──→ 不得合入          │
│       │ PASS                                            │
│       ▼                                                 │
│  大元帅确认 → git commit → 合入 main/upgrade            │
└─────────────────────────────────────────────────────────┘
```

**实施方式**（不依赖外部 CI，本地可验）：

```bash
# 在合入前运行
PYTHONPATH=backend venv/bin/python3 -m pytest backend -q       # 全量单测
venv/bin/python3 backend/common/run_kernel.py gate-pass-rate-l1 \
  --goal "..." --mode one_shot --budget 20000                  # Level 1 验证
```

### 5.3 回归项目集（Regression Suite）

三类测试，分层运行：

| 层次 | 内容 | 运行时机 | 耗时目标 |
|------|------|---------|---------|
| **单元测试** | `pytest backend -q`（当前 53 例） | 每次改动 | <60s |
| **Gate 烟雾测试** | 单任务 `research` gate 首过率（Level 1） | 每次影响 prompt/Gate 的改动 | <5 min |
| **E2E 验证项目** | Level 2 hotfix 三角色全流程 | 每次影响编排流程的改动 | <30 min |

### 5.4 指标看板（可从 SQLite 直接查）

以下指标可通过查询 `business/tasks/state.db` 获取，建议做成 `scripts/metrics.py`：

```sql
-- Gate 首次通过率（按 task_type）
SELECT task_type,
       COUNT(*) total,
       SUM(CASE WHEN gate_retries = 0 THEN 1 ELSE 0 END) first_pass,
       ROUND(100.0 * SUM(CASE WHEN gate_retries = 0 THEN 1 ELSE 0 END) / COUNT(*), 1) pct
FROM tasks
WHERE status = 'completed'
GROUP BY task_type;

-- 任务完成时间 p50/p95（秒）
SELECT task_type,
       ROUND(AVG(duration_s), 1) avg_s,
       MAX(duration_s) max_s
FROM tasks
WHERE status IN ('completed', 'failed')
GROUP BY task_type;

-- triage 触发频率（系统健康度信号）
SELECT DATE(created_at) day, COUNT(*) triage_count
FROM tasks WHERE task_type = 'triage'
GROUP BY 1 ORDER BY 1;
```
