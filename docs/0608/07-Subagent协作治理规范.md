# Subagent 协作治理规范

**生效日期**：2026-06-08  
**主控角色**：Cursor 主 Agent（汇总、门禁、文档归档）  
**专业 Subagent**：架构师 / 产品主控 / QA / 开发

---

## 一、原则

1. **开工前需求一致**：四路 subagent 对「做什么、不做什么、验收标准」签字后再写代码
2. **完工后预期一致**：四路 subagent 对「实现了什么、未实现什么、与目标差距」交叉验证后再合入
3. **主控不替代专业判断**：主 Agent 汇总共识、发现分歧、组织裁决，不独自拍板技术细节
4. **文档按日归档**：每次对齐/评审结论写入 `docs/MMDD/`

---

## 二、单 Sprint 流程（四阶段）

```
Phase 0 需求对齐（开工门禁）
    ↓ 四路一致 + 主控汇总《需求对齐纪要》
Phase 1 实施（开发 subagent）
    ↓ 代码 + 单测
Phase 2 交叉评审（架构 + QA + 产品）
    ↓ 各出评审稿；分歧由主控组织裁决
Phase 3 预期对齐（完工门禁）
    ↓ 四路确认与 Phase 0 一致；《功能预期对齐纪要》
Phase 4 主控归档 + 更新路线图/KPI
```

---

## 三、各角色职责

| 角色 | Phase 0（需求） | Phase 1 | Phase 2（评审） | Phase 3（预期） |
|------|----------------|---------|----------------|----------------|
| **产品主控** | 用户故事、不承诺项 | — | 功能是否符合用户感知 | 签字：用户可演示范围 |
| **架构师** | 层级边界、invariant | — | 是否违反 D1/D11 等 | 签字：架构合规 |
| **QA** | KPI 阈值、REG 映射 | — | pytest + 验收清单 | 签字：可证明性 |
| **开发** | 改动点、工作量、依赖 | 实施 | 回应评审意见 | 签字：端到端可跑 |
| **主控** | 汇总共识、冻结范围 | 派工 | 裁决分歧 | 发布 Sprint 结论 |

---

## 四、开工门禁 checklist（Phase 0 通过条件）

- [ ] 范围冻结：本 Sprint **做** / **不做** 清单明确
- [ ] 验收指标：每项对应 KPI 或 REG，阈值数字写明
- [ ] 依赖顺序：前置项已满足（如 L1 未完成不开 L2）
- [ ] 四路无未裁决分歧（有分歧须写入《分歧与裁决》节）
- [ ] 主控发布《需求对齐纪要》至 `docs/MMDD/`

---

## 五、完工门禁 checklist（Phase 3 通过条件）

- [ ] pytest 全绿（或 xfail 有说明）
- [ ] QA 对照 Phase 0 验收清单逐项 pass/fail
- [ ] 架构师 invariant 检查 pass
- [ ] 产品确认「可演示 / 不可演示」与 Phase 0 一致
- [ ] 主控发布《功能预期对齐纪要》至 `docs/MMDD/`
- [ ] 未达标项明确归入下一 Sprint，不静默遗漏

## 七、与路线图的关系

| 路线图层 | 对应 Sprint 类型 |
|----------|-----------------|
| L1 可靠性底座 | Sprint 0~2（接通 + 回收 + 计量） |
| L2 协作机制 | Sprint 3+（并行、透传、session） |
| L3 自进化 | Sprint N+（skill、self-upgrade） |

每层发版须 REG/Level 项目通过，见 `03-QA度量与回归体系.md`。
