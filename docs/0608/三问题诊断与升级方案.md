## 1. 问题①：切换 agent 会停掉前一个 agent 的对话

### 1.1 现象与复现
让 `main` 跑任务（显示「执行中」）→ 切到产品 agent 让它也跑任务 → 切回 `main`，**两个任务都停了**。

### 1.2 根因（前端单一全局流 + 切换即 abort，后端忠实地杀子进程）

整个前端**只有一套**流式状态槽，没有按 agent 区分：

```js
// frontend/ui-core.js:2-9
const S = {
  ...
  isStreaming: false, abortCtrl: null, currentReader: null,
  streamContext: null,
  agentEventSource: null,   // 后台事件源同样是单例
  agentTaskBlocks: {},      // ← 唯一已按 agentId 索引的（后台渲染用）
```

切换 agent 第一行就无条件中断当前流：

```js
// frontend/chat.js:83-84
function selectAgent(id, opts = {}) {
  if (S.isStreaming) stopStream();   // ← 触发源
```

```js
// frontend/ui-core.js:365-368
function stopStream() {
  if (S.abortCtrl) { S.abortCtrl.abort(); S.abortCtrl = null; }
  if (S.currentReader) { S.currentReader.cancel().catch(() => {}); S.currentReader = null; }
}
```

而 `sendAgentMsg` 每次发送都把这套单槽据为己有（`chat.js:165,174-178`：`S.isStreaming=true`、`S.abortCtrl=new AbortController()`、`S.currentReader=reader`），所以 `abortCtrl` 永远只指向**最后一次**发送。

**后端忠实地把 abort 变成真杀进程**（不是 UI 假象，已逐行核实）：

```
fetch.abort()  → TCP 断开
→ sse_bridge.py:40-42   if await request.is_disconnected(): cancel.set()
→ chat_service.py:84,170  RunRequest(cancel_event=cancel_event)
→ opencode/adapter.py:157-165  watcher 线程 ev.is_set() → self._terminate_group(p)
→ opencode/adapter.py:204-226  SIGTERM 整组 → 2s → SIGKILL
```

（`claude` 适配器同构，bug 与后端无关，源头在前端单槽。群聊 `group.js` 共用同一套全局，问题同形。）

### 1.3 为何与复现精确吻合
1. main 跑任务 → `S.abortCtrl=ctrl_main`，main 子进程在跑；
2. 切到产品 → `selectAgent` 第 84 行 abort 掉 `ctrl_main` → **main 子进程被杀**；
3. 产品跑任务 → `S.abortCtrl=ctrl_product`（覆盖）；
4. 切回 main → 第 84 行又 abort 掉 `ctrl_product` → **产品子进程被杀**。

→ 两个任务都停 = 精确复现。`AbortError` 还会走 `rollbackAgentTurn`（`ui-core.js:373`）把气泡回滚，所以观感是「对话被撤回/停住」。

### 1.4 升级方案（按 agent 隔离数据流 —— 唯一带重构性质的一项）

后端本就按请求隔离 `cancel`（每个 `/api/chat/{id}` 独立，另有 `/api/agents/{id}/events` 后台广播），**无需改动**。问题全在前端单槽，改动收敛在 `chat.js` + `ui-core.js`（群聊镜像到 `group.js`）：

1. **流状态按 agentId 注册表化**：把 `isStreaming/abortCtrl/currentReader/streamContext` 替换为
   `S.streams[agentId] = { abortCtrl, reader, ctx, busy }`。
2. **`sendAgentMsg` 绑定捕获的 agentId**：开头 `const aid = S.currentAgentId`，发送守卫改判 `S.streams[aid]?.busy`，控制器存入 `S.streams[aid]`，`finally` 里只清自己这一项。
3. **删除 `selectAgent:84` 的切换即 abort**。切换只做「重渲染选中 agent 的消息 + 重新挂载监听」，绝不中断别人。
4. **渲染数据优先、DOM 按当前 agent 动态解析（Phase 2）**：流循环每个事件先更新 `aMsg`（数据，落在 `S.agentMessages[aid]`），DOM 仅在 `aid === S.currentAgentId` 时写入。注意：`ensureAgentTaskBlock`（`chat.js:215-250`）是为**后台任务执行面板**设计的，**不是聊天气泡**；聊天气泡 DOM 在 `renderAgentMsg` / `handleChatEvent` / `updateThinkingHeader` 等路径生成，这些函数目前没有按 agentId 隔离的设计。Phase 2 实际要做的是：
   - 所有写 DOM 的函数改为「**先写数据 + 条件写 DOM**」双模式；
   - 切回 agent 时**重渲染整个可见消息区**（旧 DOM 已被 `innerHTML=''` 清除）；
   - 处理增量追加时的**滚动位置保持**。
   不能简单复用 `ensureAgentTaskBlock` 模式，需按聊天气泡路径单独改造。
5. **状态/发送按钮去全局化**：`setStatus`/`updateSendBtn`（`ui-core.js:347-364`）改读 `S.streams[S.currentAgentId]?.busy`，让按钮反映「当前 agent」状态，别人后台继续跑。
6. **停止只停当前**：`cancelActiveStream`（`ui-core.js:369-372`）只 abort `S.streams[S.currentAgentId]`。
7. **`agentEventSource` 单例**：切换 agent 会 `disconnectAgentEvents()`，需改为 per-agent 或切换时不断开非当前连接（否则后台 thinking 丢失）。

> **取舍 / 分期（评审修订）**：
> - **Phase 1**（估时 ~1d）：只做 1+2+3+5+6+7 + **`group.js` 镜像**（单聊↔群聊互斥与 FIX-① 同根，须同期修）。用户切回 agent 时看到**完成态快照**（数据已在 `S.agentMessages[aid]` 累积），**不是**后台实时滚动。
> - **Phase 2**（估时 **2–2.5d**，原 1–1.5d 偏低）：第 4 点跨 agent 实时渲染——涉及聊天气泡全链路 DOM 双模式改造，工作量大于「动态解析 el」。
> **置信度 ~95%**（杀流链路已逐行引用；Phase 2 DOM 改造范围经评审上调）。

### 1.5 验收标准
- 同时让 ≥2 个 agent 跑任务，来回切换，**两条流都继续**直到各自完成；
- 「停止」按钮只停当前 agent，不影响其它；
- 切回某 agent 能看到其在后台累积/完成的内容；
- 群聊路径同样不被单聊切换波及。

## 2. 问题②：DAG / 时间线页面空白

### 2.1 根因（前端一行字段名 bug，连坐时间线）

后端把任务字段重命名为 `id`，**返回对象没有 `task_id` 键**：

```python
# backend/common/observability.py:84
"tasks": [{"id": t["task_id"], "name": t.get("name", ""), "status": t["status"], ...
```

DAG 渲染器却在同一文件里自相矛盾——`:21` 防御性读 `t.id || t.task_id`，`:37` 却只读 `t.task_id`（=`undefined`）：

```js
// frontend/dag-renderer.js:21   （正确）
tasks.forEach(t => { byId[t.id || t.task_id] = { ...t, deps: t.dependencies || [] }; });
// frontend/dag-renderer.js:37   （错误）
tasks.forEach(t => { try { assignLevel(t.task_id); } catch(_) { level[t.task_id] = 0; } });
```

后果链（已用真实任务形状执行复现）：`level` 全是 `"undefined"` 键 → `layers={0:["undefined"]}` → `:57-59` `const t = byId["undefined"]`（=`undefined`）→ **`TypeError: Cannot read properties of undefined (reading 'name')`**。异常发生在 `:99` `container.innerHTML=svg` **之前**，故 DAG 容器永远空白。

**时间线被同一个异常连坐**——两段渲染在**同一个 `try` 里、DAG 在前**：

```js
// frontend/project.js:191-219
if (tasks.length && typeof renderDAG === 'function') {
  ...
  if (dagContainer) renderDAG(dagContainer, tasks);   // ← 在此抛异常
}
if (typeof renderTimeline === 'function') {            // ← 永不执行
  ...
  if (tlContainer && mappedEvents.length) renderTimeline(tlContainer, mappedEvents);
}
// :221  catch(e) { DOM['project-meta'].textContent = `${id} · 加载失败：…`; return false; }
```

DAG 一抛即跳到 `:221` 的 `catch`，时间线段（196-218）整段跳过。时间线渲染器本身没毛病。

### 2.2 证据（活库——数据是有的，不是 no-data）
- `run_event`：`tool_use=600, text=31, session=13, gate_passed=10 …`（合计约 697 行）；
- 项目 `critique-myteam-v3`（completed），`task=5`，含真实依赖边（如 `t5` 依赖 `t1..t4`），`project_id` 全部一致；
- 后端 `project_overview().tasks[0]` 键 = `['id','name','status','agent','dependencies','summary']`，**无 `task_id`**；`project_events` 返回 661 条。
- 故断点是 **前端抛异常不渲染**，非「无数据 / project_id 不匹配 / 容器缺失 / API 空返回」。

### 2.3 升级方案
- **主修（1 行）**：`dag-renderer.js:37` 改为与 `:21` 一致的防御读：
  ```js
  tasks.forEach(t => { const tid = t.id || t.task_id; try { assignLevel(tid); } catch(_) { level[tid] = 0; } });
  ```
  DAG 渲染恢复，且不再抛异常 → 时间线段恢复执行。后端不改（`task_id→id` 是 `project.js` 全局沿用的既定契约）。
- **可选加固（防御纵深，非必须）**：
  1. `project.js` 把 DAG / 时间线拆到各自 `try`（或时间线先渲），一个挂了不连累另一个、不污染 `project-meta`；
  2. `dag-renderer.js:57` 加 `const t = byId[id]; if (!t) return;` 守卫，杜绝游离 id 抛异常；
  3. （体感优化，独立项）时间线大量 `run_event` 落到 `'project.event'` 兜底标签，可按需补 `TL_TYPE_META` 让行有具体语义——属另一个「显示但泛化」的小问题，非本次「空白」根因。

### 2.4 验收标准
- 打开任意已完成项目的 DAG / 时间线子页能看到节点/事件；
- 概览 `project-meta` 不再出现「加载失败：Cannot read properties of undefined」；
- `refreshProjectDetail` 返回 `true`（SSE 不再每 tick 重抛）。

## 3. 问题③：成本计算恒为 0 token

### 3.1 根因（claude 适配器只在终止行报 usage + 框架提前 2.5s 杀进程）

计量代码**只认 `step_finish` 事件**才记 token：

```python
# backend/common/agent_port.py:230-234（_drain 内）
if kind in ("step_finish", "step-finish") and isinstance(payload, dict):
    t = _extract_tokens(payload)
    tokens = max(tokens, t)
    if t > 0:
        self.store.bump_interaction_tokens(iid, t)
```

但 **claude 解析器只在最后那条 `result` 行才发 `step_finish`**，逐条 `assistant` message 自带的 `usage` 被丢弃：

```python
# backend/adapters/claude/parser.py:69-88  assistant 分支：读了 content，唯独没读 msg.get("usage")
# backend/adapters/claude/parser.py:90-99  仅 result 行 emit STEP_FINISH + _extract_usage_tokens(raw)
```

而 `result` 行**永远等不到**——agent 用 `submit_result` 中途把 `.response` 落盘后，框架只宽限 **2.5 秒**就杀进程：

```python
# backend/common/agent_port.py:157-172
resp = self._read_valid_response(resp_path, iid, req_mtime)
if resp is not None:
    grace_deadline = time.monotonic() + 2.5     # 注释自承："短暂收尾以接收 Claude result 行的 step_finish"
    while th.is_alive() and time.monotonic() < grace_deadline:
        _, tok = self._drain(q, iid)
        if tok > 0: break
        time.sleep(0.05)
    ctx._cancel.set()                            # ← 杀 claude；唯一的 usage 来源 result 行未到
    th.join(timeout=3.0)
```

→ 无 `step_finish` → 计量从不触发 → tokens 恒为 0。`finalize_interaction`（`agent_port.py:308-316`）的兜底用 `event_tokens`（0）或 `meta.tokens`（agent 不自报）→ 同样 0。

**对照 opencode（为何它没这问题）**：opencode 解析器**每个 step 都发 `step_finish`**，且报的是会话**累计 total**（单调递增）：

```python
# backend/adapters/opencode/parser.py:60-73   每步 emit step_finish + tokens{input,output,total}
# backend/common/agent_port.py:219（注释）     "opencode step_finish 报会话累计 total，故取 max"
```

这些 step_finish 在运行中、`.response` 落盘**之前**就到了，所以 `_drain` 能在杀进程前计到。**这就是 claude 与 opencode 的不对称根源**。

### 3.2 全链路裁定

| 阶段 | 判定 | 说明 |
|------|------|------|
| (a) CLI 发 usage | 实质 BROKEN | claude 在 `result` 行 + 每条 `assistant.message.usage` 都有；前者被提前杀掉，后者被解析器忽略 |
| (b) Parser 提取 | **BROKEN/不足** | `claude/parser.py` 只读 `result.usage`，漏 `assistant.message.usage` |
| (c) AgentEvent 字段 | OK | 通用 `data` dict 可载 `tokens` |
| (d) AgentPort 记录 | 代码 OK / 实质 BROKEN | `_drain` 计量正确，但 `_attempt` 2.5s 后杀掉生产者，`step_finish` 从不到 |
| (e) Store 写 | OK | `bump_interaction_tokens` → `interaction.tokens`（MAX） |
| (f) 查询求和 | OK | `tokens_total`/`tokens_grouped`/`cost()` 同列 `SUM(tokens)` |

### 3.3 证据（活库）
```
interaction: n=8, sum(tokens)=0, max(tokens)=0
run_event:  tool_use=600, text=31, session=13, response_snapshot=13, prompt_sent=13,
            gate_passed=10, …  step_finish=0   ← 关键
```
600 条 tool_use 证明 claude 跑了大量消耗 token 的实活，却一条 `step_finish` 都没捕获。Store / 查询两端正确，**不要动**。

### 3.4 升级方案（必须在唯一允许耦合 claude 格式处 `claude/parser.py` 修，遵守 adapter 隔离）

> 三选一，推荐 **A（+可选 C）**。核心难点是**聚合语义**：claude 的 per-message usage 是「增量」（input 随上下文增长、output 逐条产出），不能像 opencode 的「会话累计 total」那样无脑取 MAX，否则 token 非零但偏小。

| 方案 | 做法 | 优点 | 缺点 | 取舍 |
|------|------|------|------|------|
| **A 解析器采 assistant.usage（推荐）** | `assistant` 分支读 `message.usage`，发 step_finish 携该条 usage | 运行中即到、**零额外延迟**、必非零 | 需正确累加（见下） | per-message usage 在 `.response` 落盘前就到，能在杀进程前计到 |
| B 生命周期等 result 行 | 加大 grace / 专等一个 `result`/`step_finish` 再 `cancel`（封顶如 8–10s） | 用权威累计、无解析/Store 改动 | **每次交互加延迟**；turn 不及时结束仍会漏 | 仅作兜底 |
| C 二者皆做 | A 保运行中非零 + B 在拿得到时优先用权威终止值 | 最稳 | 改动面最大 | 作为加固 |

**A 的聚合细节（实施时用测试锁定，避免少算）**：
- 解析器保持**无状态**（`parse_line` 单行进出），发 per-message **增量** `{input, output}`，并在 payload 标注非累计（如 `"cumulative": false`）；opencode 与 claude `result` 行标 `cumulative: true`。
- `_drain` 据该标志选择语义：`cumulative=true` → `bump_interaction_tokens`（MAX，现状）；`cumulative=false` → 累加。累加可落在 **AgentPort 运行态**（维护 `self._token_acc += delta` 后 `bump(iid, running_sum)`，Store 仍 MAX-of-running-sum，单写者）或新增 `store.add_interaction_tokens`（ADD）。
- 计费近似目标（**两种算式，单测择优定稿**）：
  - **算式 A**：`total ≈ max(input_i) + Σ output_i` — input 随上下文单调增长时，可能**少算**（中间轮的 input 已含历史上下文）。
  - **算式 B（倾向推荐）**：`total ≈ Σ input_i + Σ output_i` — 每条消息独立累加，可能比 Anthropic 账单**略高**（重复计上下文），但不会系统性少算。
  - **实施**：用真实 transcript 对两种算式与账单/CLI `result.usage` 做偏差对比，选定一种并在 UI hint 标注「近似值」。

### 3.5 验收标准
- 跑一次 claude 后端交互后 `interaction.tokens > 0`，`cost()` 三个口径（project/by_agent/by_task）非 0；
- 单测：喂入含 N 条 `assistant.usage` + 1 条 `result.usage` 的 transcript，断言累计 token 与预期一致（在「.response 落盘即杀」时序下仍非零）；
- opencode 路径计量不回归（仍取累计 total）。

## 4. 总体升级裁定与分期

**不需要大升级 / 重写。** 三者是定位明确、改动收敛的缺陷：

- **P0 ②**：`dag-renderer.js` 1 行 +（可选）`project.js` 拆 try。零风险，先合。
- **P1 ③**：`claude/parser.py` 采 `assistant.usage` + `agent_port._drain`/Store 聚合语义；附单测。低风险。
- **P1 ①**：`chat.js` + `ui-core.js` + **`group.js`（必做镜像）** 按 agent 隔离流。中风险，需并发实测；Phase 1「不杀流 + 切回快照」→ Phase 2「跨 agent 实时渲染」（**2–2.5d**）。后端零改动。

**影响面**：①仅前端；②仅前端一行（后端契约不动）；③仅 `backend/adapters/claude` + `agent_port` 计量分支 + Store（一处）。均不触及 kernel 调度 / Gate / contracts，不违反 adapter 隔离与交互契约不变量。

**建议落地顺序**：② →（合并验证）→ ③ → ①（先「不再杀流」，再「跨 agent 实时渲染」）。每步配独立验收，互不阻塞。

## 5. 不做清单 / 已知盲区
