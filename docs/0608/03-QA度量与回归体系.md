## 一、核心 KPI 定义（工业级协作框架）

### KPI 表

| # | KPI 名称 | 定义 | 测量粒度 | 当前值 | 目标值 |
|---|---------|------|---------|--------|--------|
| **K1** | **叶子任务完成率** | `done` 或 `needs_review` 的叶子任务数 / 叶子任务总数 | 每次项目运行 | **25%** | ≥ 80% |
| **K2** | **Gate 首次通过率** | 第 1 次 attempt 即 Gate pass 的任务数 / 总任务数 | 每次项目运行 | 不可测（超时先杀） | ≥ 70% |
| **K3** | **超时误杀率** | 被 CLAUDE_TIMEOUT 墙钟终止（非 idle watchdog 正常终止）的任务数 / 总任务数 | 每次项目运行 | **75%** | < 5% |
| **K4** | **孤儿交付物回收率** | reconcile 阶段成功 Gate 采纳的孤儿 deliverable 数 / 写到磁盘但未 submit 的交付物总数 | 每次 reconcile | **0%**（B1 未落地） | ≥ 95% |
| **K5** | **token 计量准确率** | `sum(tokens) > 0` 的 interaction 数 / 总 interaction 数 | 每次项目运行 | **0%** | 100% |
| **K6** | **算力利用率** | 状态为 `done/needs_review` 的 interaction 所用时长 / 总 interaction 时长 | 每次项目运行 | **~19%** | ≥ 75% |
| **K7** | **triage 有效决策率** | triage 给出"非原样重试"决策（拆分/升级配额/中止）的次数 / 确定性失败次数 | 每次 triage 触发 | **0%**（盲目重试） | ≥ 80% |
| **K8** | **并行度（P2 后）** | 单项目平均同时 in_progress 任务数 / 无依赖叶子任务数 | 每次项目运行 | **~0.25**（串行） | ≥ 0.8 |

### KPI 采集方法

```sql
-- K1: 叶子任务完成率
SELECT
  SUM(CASE WHEN status IN ('completed','needs_review') THEN 1 ELSE 0 END) * 1.0 / COUNT(*)
FROM tasks
WHERE project_id = ? AND (SELECT COUNT(*) FROM task_deps WHERE child_id = task_id) = 0;

-- K3: 超时误杀率（依赖 run_event 记录 reason）
SELECT
  SUM(CASE WHEN json_extract(meta,'$.fail_reason') = 'timeout_wallclock' THEN 1 ELSE 0 END) * 1.0
  / COUNT(*)
FROM tasks WHERE project_id = ?;

-- K5: token 计量准确率
SELECT
  SUM(CASE WHEN tokens > 0 THEN 1 ELSE 0 END) * 1.0 / COUNT(*)
FROM interactions WHERE project_id = ?;
```

> K2/K6/K7 目前无法从 Store 直接采集——需在 P0 方案落地后补写 `run_event` 记录字段（见第三节）。

## 四、pytest 覆盖缺口：只有 E2E 能测的行为

### 当前单元测试的覆盖边界

当前 247 个测试全部用 **fake/mock adapter** 运行，不启动真实 CLI 进程。以下行为单元测试结构性无法覆盖：

| 缺口 # | 行为描述 | 为何只有 E2E 能测 | 对应 KPI |
|--------|---------|-----------------|---------|
| **G1** | CLAUDE_TIMEOUT 墙钟 vs idle watchdog 的竞态 | 需真实 `subprocess` + 真实时间流逝；mock 不能模拟 SIGTERM 发送时序 | K3 |
| **G2** | token 计量从 claude CLI 真实 stdout 解析 | parser 单测存在（test_claude_parser.py），但 AgentPort.bump_interaction_tokens 的真实 Store 持久化链路只有 E2E 可测 | K5 |
| **G3** | 孤儿 deliverable 的 Gate 校验路径（真实文件系统 + reconcile_on_start 全链） | test_agent_port.py 的 reconcile 测试仅覆盖 `.response` 孤儿，不覆盖 `deliverables/` 孤儿 | K4 |
| **G4** | `skill_config.json` → `_run_kernel_bg` → `WatchdogConfig` 参数传递 | server.py 的 `_run_kernel_bg` 只有 test_projects_api 的 mock 测试，不验证参数值真实传入 Process | K3, K1 |
| **G5** | triage 看到真实 fail_reason 后的非原样重试决策 | triage 的 LLM 响应不可 mock；需真实 claude 返回 JSON 决策，才能验证"不盲目重试" | K7 |
| **G6** | 多任务并行时 Store busy_timeout 下的 WAL 并发 | 单连接 mock 无法重现 `database is locked`；需多线程 + 真实 SQLite WAL | K8, K1 |
| **G7** | AGENTS.md / rules 注入后 agent 实际行为改变 | rules 影响的是 LLM 输出质量（格式遵从度、结构完整性），只有真实 CLI 运行才能验证行为改变 | K2 |
| **G8** | 真实 CLI 长生成（>5min）时 idle watchdog 周期性探活 | FakeOpencode 同步返回，不能模拟"10min 内周期吐 stream-json 行"的 opus 行为 | K3 |

> **结论**：G1/G3/G4/G8 是 P0 改动的核心验证点，**必须通过 REG-01 ~ REG-03 E2E 试跑才能确认**。单元测试补充 G2/G3 的路径逻辑，但无法替代真实 CLI 验证。

### `run_regression.sh` 逻辑结构

```bash
#!/bin/bash
# 用法: ./scripts/regression/run_regression.sh [--suite unit|e2e|all] [--project reg-01]
# 退出码: 0=全通过, 1=警戒线触发, 2=阻断级失败

set -e
SUITE=${1:-all}
TIMESTAMP=$(date +%Y%m%d-%H%M%S)
REPORT_DIR="/tmp/myteam-regression-$TIMESTAMP"
mkdir -p "$REPORT_DIR"

# ---- Phase 1: 单元测试（快，<15s）----
if [[ "$SUITE" == "unit" || "$SUITE" == "all" ]]; then
  echo "=== Phase 1: Unit Tests ==="
  PYTHONPATH=backend python3 -m pytest backend/common/tests/ -q --tb=short \
    --ignore=backend/common/tests/test_r2_features.py \   # 排除假绿
    -o "junit_family=xunit2" --junitxml="$REPORT_DIR/unit.xml"
  # 阈值: 必须 100% pass（0 failure）
```
