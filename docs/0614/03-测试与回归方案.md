## 1. 测试金字塔

本方案按四层组织验证，自底向上成本递增、覆盖面递增：

| 层级 | 范围 | 工具 | 触发时机 | 目标时长 |
|------|------|------|----------|----------|
| **Unit** | `loop_runtime` 纯函数、YAML 解析/校验 | `pytest backend/common/tests/test_loop_runtime.py` | 每 PR | < 30s |
| **Integration** | `Process.run()` + fake transport 端到端 loop | `pytest backend/common/tests/test_process_loops.py` | 每 PR | < 60s |
| **REG (CHECK_ONLY)** | 加载真实 workflow、校验产物 KPI，**不跑 kernel** | `scripts/regression/reg_*.py` | CI `suite=v1` / 发版前 | < 2min |
| **LIVE** | `run_kernel.py` + Claude CLI 真实 agent | REG `CHECK_ONLY=0` 或手工 | P1/P2 里程碑、发版前 | 10–60min |

**原则**：CI 默认只跑 Unit + Integration + CHECK_ONLY REG；LIVE 失败不阻塞日常 PR，但阻塞 P1/P2 阶段验收与发版。

## 2. Fake Transport 模式（集成测试基线）

沿用 `test_process_loops.py` 已验证的模式，所有 v2 集成用例复用同一套 fixture：

```python
@pytest.fixture()
def env(tmp_path, monkeypatch):
    # 隔离 WORKSPACES_DIR / PROJECTS_DIR / agents_registry
    # Store + WatchdogConfig(poll_interval=0.02)
```

**Transport 约定**（`AgentPort(transport, ...)`）：

1. 按 `ctx.request.task_id` 后缀分发：`endswith("-work")` / `endswith("-assess")` / `endswith("-review")`。
2. `_write(ctx, content, quality)`：写 `deliverables/{task_id}_deliverable.md`，调用 `submit()` 模拟 agent 回包。
3. `_valid(task_type)`：用 `get_spec(tt).required_sections` 生成 Gate 合规正文。
4. `_acceptance_with_marker(marker)`：在 review/assess 交付物末行附加 marker（`REVIEW: PASS` / `ITERATION: CONTINUE` 等）。
5. `_ensure_process_artifacts(project_id)`：预置 `align.md`、`verify.log`，避免 process 前置校验失败。

**v2 扩展**：transport 需感知 `body_key`（通过 task id 中 `-r{n}-` 与 body 内 task id 推断），并在 `next_body=patch` 时验证 `seed_patch_baseline` 是否复制上一轮 work 交付物。

## 4. v1 向后兼容矩阵

以下场景在 **P0–P2 全程** 必须保持行为不变（任一失败即阻塞合并）：

| 场景 | Workflow / Spec | 验证方式 | 期望 |
|------|-----------------|----------|------|
| V1-C01 | `产品规划方案.yaml` `ch3_quality_round` | `test_load_product_planning_workflow_v2_with_loops` | version 2.2，loop id 不变 |
| V1-C02 | 首轮 `REVIEW: PASS` | `test_loop_passes_on_first_round` | 1 轮 review，占位 completed |
| V1-C03 | 全程 `REVIEW: FAIL` | `test_loop_exhausts_after_max_rounds` | max_rounds 耗尽 → needs_review |
| V1-C04 | 第 3 轮 PASS | `test_loop_passes_on_third_round` | 3 轮后 completed |
| V1-C05 | FAIL + 群讨论 | `reg_discuss_loop.py CHECK_ONLY` | r1 FAIL + group_discussion + r2 PASS |
| V1-C06 | `evaluate_until` + `until` | `test_evaluate_until_deliverable_marker` | 不经过 assess 仍可用 |
| V1-C07 | `seed_patch_baseline` | `test_seed_patch_baseline` | 多轮 work 复制逻辑不变 |
| V1-C08 | recurring `max_cycles` | `reg_k16_recurring_trigger.py`（framework suite） | 与 iteration 正交，无回归 |

**兼容策略**：v1 YAML 仅含 `body`+`until` 时，解析器注入 `default_body=default`、`bodies={default: body}`，运行时走 v1 代码路径或等价分支，**禁止**要求业务方改 YAML。

## 5. 新增 REG 脚本规格

### 5.1 `reg_iteration_assess.py`（P1）

**目的**：验证 `business/workflows/_examples/iteration-v2-fixture.yaml` 的 assess + transition 链路。

**环境变量**：

| 变量 | 默认 | 说明 |
|------|------|------|
| `REG_ITERATION_CHECK_ONLY` | — | `1` = 仅 KPI 检查 |
| `REG_ITERATION_PROJECT_ID` | `reg-iteration-assess` | CHECK_ONLY 读取的项目 |
| `REG_ITERATION_LIVE_PROJECT_ID` | `reg-iteration-assess-live` | LIVE 新建项目 |
| `REG_ITERATION_WORKFLOW` | `iteration-v2-fixture` | workflow id |
| `REG_ITERATION_LOOP_ID` | `wave` | loop id |
| `REG_ITERATION_BUDGET` | `REG_DEFAULT_BUDGET` | LIVE token 预算 |

**CHECK_ONLY 流程**：

1. `_check_loader()`：`load_workflow` → `instantiate_tasks` → `check_plan`；断言含 `bodies`、`assess`、`transition`。
2. `_check_artifacts(project_id)` KPI：
   - 存在 `{loop}-r1-assess_deliverable.md`，末行含 `ITERATION: CONTINUE` 或归档等价；
   - 存在 `{loop}-r2-assess_deliverable.md`，末行含 `ITERATION: PASS` 或 `REVIEW: PASS`；
   - 占位 task 对应 deliverable 或 `state.db` 中 status=`completed`；
   - `run_event` 含 `loop_transition`（可选：查 `state.db` events 表）。
3. 产物不完整时：fallback `last_pass_run("REG-ITERATION")` 归档（对齐 `reg_discuss_loop.py`）。

**LIVE 流程**：

1. 检测 `claude` CLI；不可用 → exit `2` SKIP。
2. `subprocess.run([venv/python, backend/common/run_kernel.py, live_pid, --workflow, ...])`。
3. `_check_artifacts(live_pid)` + `_project_status == completed`。
4. `append_run_record(reg_id="REG-ITERATION", ...)`。

**退出码**：`0`=PASS，`1`=FAIL，`2`=SKIP（无 CLI）。

### 5.2 `reg_geo_iteration.py`（P2）

**目的**：验证 `GEO持续优化-迭代.yaml` 多 body 分支（audit→revise→verify + patch branch）。

**环境变量**：

| 变量 | 默认 | 说明 |
|------|------|------|
| `REG_GEO_ITER_CHECK_ONLY` | — | `1` = 仅 KPI |
| `REG_GEO_ITER_PROJECT_ID` | `reg-geo-iteration` | CHECK_ONLY 项目 |
| `REG_GEO_ITER_LIVE_PROJECT_ID` | `reg-geo-iteration-live` | LIVE 项目 |
| `REG_GEO_ITER_WORKFLOW` | `GEO持续优化-迭代` | workflow id |
| `REG_GEO_ITER_LOOP_ID` | `geo_wave` | loop id（以 YAML 为准） |

**CHECK_ONLY KPI**：

1. Loader：`bodies` 至少含 `default` 与 `patch`（或 YAML 声明的分支名）；`expand_loop_body_for_validation` 通过。
2. r1：`{loop}-r1-assess` 末行 `ITERATION: CONTINUE` 或 `REVIEW: FAIL`；存在 `branch_selected` 事件或 r2 body 任务 id 含 patch 分支特征。
3. r2：执行 patch body（如 `{loop}-r2-revise` 与 default 不同 agent/task_type）；assess 末行 `ITERATION: PASS`。
4. 占位节点：`completed`；`meta.loop_state` 含 `branched`（若写入 state）。

**LIVE**：同 `reg_iteration_assess`，workflow/goal 换为 GEO 场景；预算建议 ≥ 2× REG_DEFAULT_BUDGET（三轮 agent）。
