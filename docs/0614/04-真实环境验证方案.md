## 1. 目的与范围

本方案定义在 **真实 macOS/Linux 环境** 下，用 Claude CLI + Hub 2.0 UI 对 LoopSpec v2 能力的 LIVE 验收步骤。验证目标：

1. **Pilot A**（`产品规划方案`）：v1→v2 等价迁移后，assess/transition 与群讨论 FAIL→PATCH 路径仍可用。
2. **Pilot B**（`GEO持续优化-迭代`，P2 就绪后）：多 `bodies` 分支与 `branch_selected` 可观测。
3. **Hub v2**：`/v2/projects` 项目详情可看到轮次/事件；`/v2/workflows` 编辑器可保存 loop 配置。
4. **正交 smoke**：7 天 recurring 与 iteration 互不回归（见 §7）。

不在本方案内：OpenCode 生产基线、xhs 登录 LIVE、内核 `process.py` 行为变更审批（见 `FRAMEWORK-FREEZE.md`）。

## 3. Pilot A — 产品规划方案（P1 末 LIVE）

### 3.1 项目标识

| 字段 | 值 |
|------|-----|
| `project_id` | `live-pilot-a-ch3`（可覆盖 `LIVE_PILOT_A_ID`） |
| `workflow` | `产品规划方案` |
| `loop_id` | `ch3_quality_round` |
| `goal` | 使用 `business/workflows/README.md` 中 TDS 第三章 goal 或简短：「可信数据空间第三章产品整体规划」 |
| `backend` | `claude` |
| `budget` | `800000`（告警阈值 80% = 640000 tok） |

### 3.2 CLI 启动（Runbook）

```bash
export MYTEAM_ROOT="$PWD" PYTHONPATH="$PWD/backend"
export LIVE_PILOT_A_ID="${LIVE_PILOT_A_ID:-live-pilot-a-ch3}"
export LIVE_BUDGET="${LIVE_BUDGET:-800000}"

# 清理旧试跑（可选，慎用）
# rm -rf "business/tasks/project/${LIVE_PILOT_A_ID}"

venv/bin/python3 backend/common/run_kernel.py "$LIVE_PILOT_A_ID" \
  --workflow 产品规划方案 \
  --goal "可信数据空间：撰写第三章产品整体规划并完成质量评审" \
  --budget "$LIVE_BUDGET" \
  --backend claude \
  --mode one_shot
```

**并行 Hub 观察**：浏览器打开 `http://127.0.0.1:8765/v2/projects/${LIVE_PILOT_A_ID}`（dev 模式则为 `localhost:5173/v2/projects/...`）。

### 3.3 预期内核事件（`run_event` / 项目事件流）

按时间顺序应出现（P1 后增补 assess/transition 种类）：

| 事件 kind | 含义 | 验收 |
|-----------|------|------|
| `gate_passed` | work/review 交付物过 Gate | 每轮 work、review 各 ≥1 |
| `loop_round_done` | 一轮 body 结束 | round 递增；payload 含 `loop_id`、`round` |
| `loop_round_assess` | （P1+）assess 步完成 | 若已迁移 v2 bodies |
| `loop_transition` | （P1+）marker 解析结果 | `action` 为 `continue` 或 `exit` |
| `message` / 群讨论 | FAIL 后 `group_discussion` | r1 若 FAIL，须有群对齐记录 |
| `loop_finished` | 占位节点终态 | `outcome` 为 `complete` 或 `needs_review` |

**交付物路径**（`business/tasks/project/<id>/deliverables/`）：

- `ch3_quality_round-r{N}-work_deliverable.md`
- `ch3_quality_round-r{N}-review_deliverable.md` — 末行 `REVIEW: PASS` 或 `REVIEW: FAIL`
- FAIL 轮：`ch3_quality_round-r{N}-group_discussion.md`（含「定点改稿清单」）
- PASS 轮次 ≤ `max_rounds`（5）；**过关：3 轮内出现 PASS**（总方案 §9 KPI）

### 3.4 Hub v2 检查清单（截图）

在 **项目详情** `ProjectDetailPanel`（路由 `/v2/projects/:projectId`）采集：

| # | 检查项 | 通过标准 |
|---|--------|----------|
| S1 | 顶栏状态 + 启动配置 | 工作流=产品规划方案；CLI 后端=claude；预算显示正确 |
| S2 | DAG 页 | 占位节点 `t-ch3-plan` 最终 `completed` 或 `needs_review` |
| S3 | 执行树 `ProjectExecTree` | 可见 `loop_round_done` / `loop_finished` 里程碑 |
| S4 | 活动流 `ProjectActivityFeed` | 评审 FAIL 后有群讨论相关 `message` |
| S5 | 交付物面板 | 可打开末轮 review；末行 marker 与磁盘一致 |
| S6 | 成本页 | token 用量 < budget 80%（否则记 WARN，不单独 FAIL） |

截图存档目录建议：`docs/0614/evidence/pilot-a/<date>/`（S1–S6 各一张）。

### 3.5 Pilot A 过关判定

- `project.status == completed`
- 末轮 review deliverable 末行 `REVIEW: PASS`
- 若 r1 为 FAIL：存在 `group_discussion` + r2 work 为 PATCH（非全文重写，人工 spot-check）
- Hub S2–S5 全部通过

## 6. KPI 与过关阈值

| KPI ID | 指标 | 过关 | 失败 |
|--------|------|------|------|
| K-A1 | Pilot A 轮次 | ≤3 轮 `REVIEW: PASS` | >5 轮或 `needs_review` 且无 PASS |
| K-A2 | 群讨论路径 | r1 FAIL 时必有 group_discussion + r2 PATCH | 缺讨论或 work 全文重写 |
| K-B1 | Pilot B 分支 | ≥1 `branch_selected` | 无分支事件或占位未完成 |
| K-B2 | Pilot B 终态 | `completed` | `failed` / 永久 `running` |
| K-H1 | Hub 截图 | S1–S6（A）或 S1–S5+B 分支（B）齐全 | 缺项或 marker 与磁盘不一致 |
| K-H2 | Workflow 保存 | 保存后 reload 一致 | API 4xx 或丢失 |
| K-T1 | Token | 单 loop < budget×80% | ≥80% 记 WARN；≥100% FAIL |
| K-R1 | 7-day recurring | ≥5/7 tick completed（§7） | <5/7 |
| K-P0 | 预检 REG | v1 CHECK_ONLY 全绿 | 任一脚本 FAIL |

## 9. 回滚与中止

| 场景 | 动作 |
|------|------|
| 运行中需停止 | Hub「取消」或 `POST /api/projects/{id}/cancel`；CLI Ctrl+C 后查 `kernel_job` |
| 单任务 failed | `POST /api/projects/{id}/resume` 或 `REG_*_RESUME=1` 重跑 REG |
| Gate 反复失败 | 查 deliverable + `run_event` 中 `gate_failed`；**不**改生产 backend 为 opencode |
| budget paused | 提高 budget 或 `resume_project`；记录 K-T1 |
| 试跑污染 | 删除 `business/tasks/project/<id>/` + DB 行（慎用）；保留 forensics 后再删 |
| YAML 被 UI 误改 | `git checkout -- business/workflows/`；以 git 为真源 |
| Pilot 失败需回退发布 | 不合并 P1/P2 PR；CHECK_ONLY 保持绿即可继续开发 |

**中止条件**：连续 2 次 LIVE 同 KPI 失败且 forensics 显示 assess marker 缺失 → 停止 LIVE，回 P1/P2 修 kernel 或 YAML。
