# 系统升级工作流

系统升级的目标是确保每次变更都**目标清晰、实现稳定、结果可追溯、不引入回归问题**，整个流程遵循五个阶段：第一阶段诊断与目标，先用日志、截图、错误信息复现问题或描述当前状态，然后明确定义升级后的目标状态——即"什么样的状态算成功"，最后确定验证方式，指定具体的测试用例、手动检查点和观测指标，产出清晰的问题描述+目标状态+验证标准，严禁不明确目标就开始改代码；第二阶段方案评审，设计具体的变更方案列出要改哪些文件和逻辑，识别风险包括可能被影响的模块、数据流和依赖关系，制定回滚策略确定出问题如何快速恢复，可用 code review、`plan-eng-review` 检查架构风险、`plan-ceo-review` 确认方案是否解决核心问题，产出可执行的变更清单附带风险和回滚计划，严禁不做风险评估就动手；第三阶段小步实现，按依赖优先级从改动最小的部分开始逐步推进，每次只改一件事保持原子性，每次变更后立即跑测试和检查日志确认无新增错误，commit message 用 `fix(模块)`/`feat(模块)`/`refactor(模块)` 格式并说明变更原因而非仅描述变更内容，严禁一个大 commit 包含多个不相关变更、改完不验证继续下一步、或 commit message 只写"fix"或"update"；第四阶段回归验证，先运行完整自动化测试套件（`PYTHONPATH="$PWD/backend" venv/bin/python3 -m pytest backend -q`），再启动服务做冒烟测试（`./run.sh start` 检查关键 API），然后按阶段 1 定义的验证标准逐一进行功能验证，最后查看日志和监控指标确认无异常，若验证不通过则定位是新问题还是老问题，修复后重新从自动化测试开始验证并记录根本原因；第五阶段提交与归档，用规范 commit message 创建提交，同步更新 `docs/` 下相关文档，在 commit 中引用本次升级的目标描述以便追溯，保留回滚能力不 force-push 已合并的分支，升级完成前必须确认：目标清晰、变更原子、测试通过、无回归、文档更新、可追溯，常见陷阱包括目标模糊导致改了不知道有没有用、改动过大导致出问题不知道哪行导致、跳过测试导致引入回归问题、不写理由导致后续无法追溯、不更新文档导致文档与代码不一致，这些都应在对应阶段通过检查清单规避。
