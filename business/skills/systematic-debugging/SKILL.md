# 系统化调试

> 来源：obra/superpowers (MIT)，适配 myteam。

## 铁律

```
没有完成根因调查，不尝试任何修复
```

随机修复浪费时间并制造新 bug。症状修复就是失败。

## 四阶段流程

必须逐阶段完成，不可跳过。

### 阶段 1：根因调查

**尝试任何修复前：**

1. **仔细读错误信息** — 不跳过 error/warning，读完整 stack trace，记录行号/文件/错误码
2. **稳定复现** — 能可靠触发吗？精确步骤是什么？每次都发生吗？不能复现→收集更多数据，不猜
3. **检查近期变更** — git diff、最近提交、新依赖、配置变更、环境差异
4. **多组件系统收集证据** — 在每个组件边界记录输入/输出/环境/状态，运行一次定位故障层
5. **追踪数据流** — 坏值从哪来？谁调用的？一直追到源头，在源头修复而非症状处

### 阶段 2：模式分析

1. 找同库中类似的**能工作**的代码
2. 完整阅读参考实现（不 skim）
3. 列出工作版本与故障版本的**每个差异**，不论多小
4. 理解依赖：需要哪些组件、配置、环境、假设

### 阶段 3：假设与测试

1. **形成单一假设** — "我认为 X 是根因，因为 Y"，写下来，要具体
2. **最小测试** — 做最小改动验证假设，一次一个变量
3. **验证后继续** — 有效→阶段 4；无效→形成**新**假设，不在旧修复上叠加

### 阶段 4：实现

1. **创建失败测试** — 最简复现，自动化测试优先
2. **实现单一修复** — 只修已定位的根因，一次一个改动，不"顺便"改进
3. **验证修复** — 测试通过？其他测试没坏？问题真的解决了？
4. **修复不生效** — 停。已尝试 <3 次→回阶段 1 重新分析；≥3 次→停止，质疑架构

### 3+ 次修复失败的架构信号

- 每次修复都暴露新耦合/共享状态问题
- 修复需要"大规模重构"才能实现
- 每次修复在别处制造新症状

→ 这不是假设失败，是架构错误。停止修复，讨论是否重构架构。

## 红旗 — 看到就停，回阶段 1

- "先快速修，回头再查"
- "改一下 X 试试看"
- "同时改多处，跑测试"
- "跳过测试，手动验证就行"
- "大概是 X，修一下"
- 没追踪数据流就提方案
- 已尝试 2+ 次还在"再试一次"

## myteam 红线

- 执行前必须 Read 本 SKILL.md 全文
- 调试须先复现再定位，禁止随机改代码试（与 USER.md principles 一致）
- Gate 验收时，`设计方案`章节须含根因分析过程
- 修复 3 次仍失败→在交付物中标注"架构问题"，不继续盲目修复
