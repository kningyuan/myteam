# 头脑风暴：把想法变成设计

> 来源：obra/superpowers (MIT)，适配 myteam。

## 硬门禁

```
未呈现设计并获得批准前，不写任何代码、不创建任何项目、不采取任何实现行动
```

每个项目都必须经过此流程——"简单"项目正是未审视的假设造成最多浪费的地方。设计可以很短（几句话），但必须呈现并获批准。

## 清单（按序完成）

1. **探索项目上下文** — 检查文件、文档、近期提交
2. **逐个提问澄清** — 一次一个问题，理解目的/约束/成功标准
3. **提出2-3个方案** — 含权衡和推荐
4. **呈现设计** — 按复杂度分节，每节后获确认
5. **写设计文档** — 保存并提交
6. **规格自审** — 检查占位符、矛盾、歧义、范围
7. **用户评审规格** — 用户评审书面规格后继续
8. **转入实现** — 调用 writing-plans 创建实现计划

## 过程要点

**理解想法：**
- 先检查项目当前状态（文件、文档、近期提交）
- 评估范围：如果请求描述多个独立子系统，立即标记，帮助分解为子项目
- 逐个提问细化想法，一次一个问题，优先用多选题
- 聚焦理解：目的、约束、成功标准

**探索方案：**
- 提出2-3个不同方案及权衡
- 对话式呈现，含推荐和理由，推荐方案在前

**呈现设计：**
- 按复杂度分节：简单的几句话，复杂的200-300字
- 每节后确认是否正确
- 覆盖：架构、组件、数据流、错误处理、测试

**设计原则：**
- 隔离与清晰：每个单元一个明确目的，通过良好定义的接口通信，可独立理解和测试
- 能回答：它做什么？怎么用？依赖什么？
- 不读内部能否理解单元？改内部会破坏消费者吗？不能则边界需调整

## 设计后

1. 写设计文档到交付物目录
2. 规格自审：占位符扫描、内部一致性、范围检查、歧义检查——发现问题就地修复
3. 用户评审门控：规格自审通过后，请用户评审书面规格
4. 实现：调用 writing-plans skill 创建详细实现计划

## 关键原则

- 一次一个问题，不 overwhelms
- YAGNI 无情——从设计中移除不必要功能
- 探索替代方案——确定前总提2-3个
- 增量验证——呈现设计，获批准再继续
- 灵活——不理解时回去澄清
