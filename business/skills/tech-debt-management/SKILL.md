# 技术债务管理方法论

> **最佳实践来源**：企业架构持续改进从技术债务到效能倍增，Code Review Checklist

## 何时启用

- `task_type` 为 `code-review`、`quality-review`、`architecture-review`
- 用户要求"技术债务""重构""代码质量""架构健康度"

## 债务分类

| 类型 | 特征 | 处理策略 |
|------|------|----------|
| 故意债务 | 有意识地走捷径，有时间表 | 到期偿还 |
| 无意债务 | 缺乏知识导致的不佳设计 | 学习+重构 |
| 腐蚀债务 | 代码随时间腐化 | 持续维护 |
| 架构债务 | 模块耦合、边界模糊 | 架构演进 |

## 量化度量（架构健康度指标）

| 指标 | 目标值 | 工具 |
|------|--------|------|
| 圈复杂度 | <10 | radon/eslint |
| 测试覆盖率 | >80% | coverage.py |
| 代码重复率 | <5% | jscpd/duplication |
| 函数行数 | Python <30行 / TS <20行 | eslint |
| 嵌套深度 | <3层 | eslint |
| 模块耦合度 | 依赖数 <7 | madge/dependency-cruiser |
| 变更失败率 | <15% | CI统计 |

**质量门禁**：将指标集成进 CI，不达标的构建自动失败。

## 优先级排序

**ROI 矩阵**（影响 × 紧急度）：

| | 高紧急 | 低紧急 |
|---|--------|--------|
| 高影响 | P0：立即修复 | P1：本迭代修复 |
| 低影响 | P2：下迭代修复 | P3：有机会再修 |

**排序因素**：
1. 变更频率 — 高频变更区域的债务优先
2. 阻塞程度 — 阻塞新功能的债务优先
3. 风险等级 — 引发线上故障的债务优先
4. 修复成本 — 低成本高收益的债务优先

## 重构策略

### 原则
- **小步快跑**：每次重构 <2 小时，可独立提交
- **行为不变**：重构前后测试结果一致
- **测试先行**：重构前先补测试，确保有安全网
- **分离进行**：重构与功能开发不混在同一 PR

### 重构模式（按优先级）

| 优先级 | 模式 | 适用场景 |
|--------|------|----------|
| 1 | 提取函数 | 函数过长（>30行） |
| 2 | 内联函数 | 函数只有一行且名称多余 |
| 3 | 提取变量 | 表达式复杂难理解 |
| 4 | 移动语句 | 相关语句应聚拢 |
| 5 | 重命名 | 名称不达意 |
| 6 | 提取类 | 类职责过多 |
| 7 | 内联类 | 类已无存在价值 |
| 8 | 替换算法 | 有更清晰的实现方式 |

### 红绿重构循环

```
红色：写一个失败的测试
绿色：用最简单的方式让它通过
重构：改善代码结构，保持测试通过
```

## 债务登记

**每条债务记录**：
- 位置：文件路径 + 行号
- 类型：故意/无意/腐蚀/架构
- 描述：具体问题
- 影响：阻塞了什么
- 修复成本：S/M/L
- 优先级：P0-P3

## 质量红线

- 禁止删除死代码前不确认依赖 — 须先搜索引用
- 禁止过度抽象 — 只在重复出现3次以上才抽象
- 禁止重构无测试保护的代码 — 先补测试
- 禁止一个 PR 混合重构与功能 — 须分离

## Gate 检查清单

- [ ] 债务分类明确（故意/无意/腐蚀/架构）
- [ ] 量化指标有目标值和工具
- [ ] 优先级排序有 ROI 矩阵
- [ ] 重构策略含小步快跑原则
- [ ] 债务登记格式完整
- [ ] 含 CI 质量门禁方案
