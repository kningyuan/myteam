# 产品方法论（myteam 适配版）

> **来源合成**（已裁剪）：
> - Jobs-to-be-Done / 用户故事映射
> - PRD 最佳实践（In/Out Scope、可测试验收）
> - RICE / MoSCoW 优先级框架
> - 验收驱动开发（Acceptance Criteria 先行）

**myteam 红线**：产品交付 **可验证结论**，不把技术实现细节写成已定方案（留给 arch / system-design）。

---

## 何时启用

- `task_type` 为 requirements、strategy、product-planning、product-research、acceptance-report、section-authoring、section-review（产品视角）
- 用户问「需求怎么写」「验收标准」「范围怎么定」

---

## 执行流程（必须按序）

### Step 1 — 问题空间（Problem Space）

| 维度 | 内容 |
|------|------|
| 用户/客户 | 谁在用、在什么情境下 |
| 痛点 | 现状为何不够好（证据引用上游 research） |
| 成功指标 | 可观察的结果（非功能清单） |
| 非目标 | 本轮明确不做的事 |

**禁止**在未写非目标前堆功能列表。

### Step 2 — 用户与场景

- 至少 **2 个** 具体场景（When / I want / So that）
- 用户故事表：`角色 | 场景 | 价值 | 优先级(MoSCoW 或 P0/P1/P2)`
- 每个 P0 故事须对应下游可执行的 **R1/R2…** 验收标准

### Step 3 — 范围边界（Scope Contract）

交付物 **必须** 含：

```markdown
## In Scope
- …

## Out of Scope
- …（至少 3 条，防止 scope creep）
```

Out of Scope 是 Gate 硬要求，不可省略或合并进正文。

### Step 4 — 可验证验收标准

每条验收标准须满足 **SMART 测试性**：

| ID | 标准 | 验证方式 |
|----|------|----------|
| R1 | 给定…当…则… | 手动步骤 / 脚本 / 演示 |
| R2 | … | … |

**禁止**：「体验良好」「性能足够」等不可测试表述。

### Step 5 — 方案方向与优先级（strategy / planning）

- 可选方案 **≥2**，用表格对比维度（成本、风险、时间、依赖）
- 推荐方案 **1 句结论** + 不选其他的首要理由
- 策略类须含 **「不确定性」**：数据缺口、待验证假设、局限

### Step 6 — 验收报告专用（acceptance-report）

- 逐项对照上游 R1/Rn：**PASS / FAIL / 遗留 / 降级**
- 无 qa 日志或脚本 exit 0 证据 → 禁止写「全部通过」
- 发布建议须与遗留项一致（有 P0 遗留 → 不得建议全量发布）

## 反模式（禁止）

- 把 UI 控件级设计写进 PRD（留给 frontend / arch）
- 无 Out of Scope 的「大而全」需求
- 验收标准无法被 qa 或脚本复现
- 策略文档无不确定性章节

---

## Pitfalls（常见踩坑）

- **冷启动瞎编**：未 Read 本 SKILL + 上游 research 就写结论 → 必须标注「待验证假设」
- **Scope creep**：In Scope 不断追加、Out of Scope 空白 → Gate 会拒
- **不可测试验收**：「体验好」「性能够」→ 改成 Given/When/Then 或可脚本化检查
- **越界写实现**：PRD 里定死 API/表结构 → 留给 arch / system-design
- **调研无过程**：全景调研须列出扫描路径、测试命令、文档/代码对照；禁止只读 README 就下结论

## 质量评估标准（Rubric — 你的交付物将按此评分）

每次执行后交付物会被自动按以下标准评估（0/0.5/1 三档）：

| 维度 | 核心要求 |
|------|----------|
| 需求目标匹配 | 不擅自扩大/缩小范围，区分显性隐性需求 |
| 交付物完整 | PRD须含：业务背景、用户角色、正常流程、异常分支、验收指标 |
| 专业准确 | 竞品/行业数据必须有来源标注，禁止编造数据 |
| 落地可行 | 须考虑技术/运营/现有系统限制，配套折中方案 |
| 产品思维 | 方案必须包含：①目标用户 ②核心痛点 ③解决方案 ④效果衡量指标 |
| 可解释性 | 每项设计附带推导依据，不直接给结论 |
| 鲁棒性 | 必须覆盖异常场景（空数据/失败/无权限） |

**红线（触发直接不及格）**：
- 编造行业数据/竞品规模且无来源标注
- 流程图仅用纯文字/ASCII 无结构化 DSL（Mermaid/PlantUML/Graphviz）
- 仅设计正常流程，完全不覆盖异常场景
- 交付物缺失背景/用户/流程/验收等必备模块

完整 rubric 见：`docs/superpowers/specs/2026-06-23-agent-prd-quality-rubric.md`

## Pitfalls（补充）

### 交付物完整性检查
- **提交前对照 rubric 逐项核对**：本次缺失「业务背景」「正常流程」两个章节，导致交付物完整度扣分。
- **建议**：在 execute 阶段结束时，用 rubric 的 required_sections 列表做 checklist 验证，确保每个 2-level header 都覆盖。

### 语言精确性
- **避免模糊不可量化词**：如「提升用户」「优化体验」等无具体指标的表述。
- **建议**：所有价值主张和功能描述必须包含可量化指标（如「DAU 提升 X%」「响应时间降低至 Yms」），或明确标注为定性判断。

## Verification（补充）
- 提交前运行：`grep -c '^## ' deliverable.md` 确认章节数量与 rubric 要求一致。
- 全文搜索模糊词模式（「提升」「优化」「改善」「更好」）并逐一替换为可量化表述。

## 竞品分析交付物完整性要求

竞品分析类任务（如 step-compare）的交付物除对比矩阵外，必须包含以下章节：

### 必含章节
1. **业务背景**：分析目的、分析范围、数据来源说明
2. **目标用户定位**：各竞品服务的主要用户群体画像
3. **能力对比矩阵**：功能/定价/体验多维度对比（已有）
4. **优劣势分析**：每产品优势/劣势，标注数据来源（已有）
5. **差异化机会**：基于对比的差异化建议（已有）
6. **落地可行性**：技术/运营/现有系统限制，P0/P1/P2 优先级标注
7. **效果衡量指标**：可量化的成功指标（如用户转化率、留存率等）
8. **异常场景覆盖**：空数据、失败状态、无权限等边界情况的处理方案

### Pitfalls
- 竞品分析容易只停留在「对比表格」层面，缺少业务上下文和落地路径
- 信息缺口必须明确标注，禁止编造数据
- 每个结论必须标注数据来源（上游交付物或原始调研）

### Verification
- 交付物必须包含上述 8 个章节
- 每个结论有可追溯的数据来源
- 异常场景有明确的处理方案描述

## 新增 Pitfalls

### 4. 模糊不可量化语言
**Problem**: 产品规划文档中使用「提升效率」「优化体验」「增强安全性」等模糊词汇，缺乏可量化指标。
**Solution**:
- 用具体数字替代模糊词：「提升效率」→「减少 X% 的处理时间」或「从 X 分钟降至 Y 分钟」
- 用可验证标准替代主观描述：「增强安全性」→「通过 OWASP Top 10 检查」或「达到 SOC2 Type II 合规」
- 每个功能描述至少包含一个可量化的验收指标

### 5. 产品规划文档章节缺失
**Problem**: 产品规划文档缺少流程类章节（正常流程、异常分支、业务流程图），导致交付物不完整。
**Solution**:
- 产品规划类交付物必须包含：正常流程、异常分支、业务流程图（至少一种可视化形式）
- 每个核心功能模块都应描述其正常执行路径和至少一个异常处理分支
- 使用流程图（Mermaid/ASCII）或表格形式呈现业务流程

## 新增 Verification 条目

### 产品规划文档质量检查
- [ ] 所有功能描述使用可量化指标，无模糊词汇
- [ ] 包含正常流程、异常分支、业务流程图
- [ ] 每个核心功能有可验证的验收标准

## Pitfall: 交付物中的模糊表述

**Problem**: 交付物中出现「提升效率」「优化体验」「改善」「更好」「有潜力」「建议完善」「逐步优化」等模糊表述，缺乏可验证的具体数据支撑，导致 Gate 判定为 needs_review。

**Solution**:
- 提交前用 grep 扫描模糊表述：`grep -nE '(提升效率|优化体验|改善|更好|有潜力|建议完善|逐步优化)' <deliverable>`
- 区分引用语（用户评价原文）与自身论断：引用语可保留，自身论断必须替换为具体数据
- 将模糊表述替换为可量化指标（如「4.5/5 星」而非「用户评价很好」）

**Verification**:
- 提交前执行模糊表述扫描，确保无自身论断类模糊词
- 质量自评应保守（0.92 仍可能触发 needs_review）

## Pitfall: 重复生成相同内容导致 token 耗尽

### 问题
Agent 在收到 rubric 反馈后，反复用 `write` 写入完全相同的交付物内容，未能实际修改。原因：reasoning 中意识到问题（"I keep writing the exact same content!"），但后续步骤仍重复相同操作，最终触发 token 上限（262144）导致 APIError。

### 根因
- 收到 rubric 反馈（如"缺少关键词：原因、背景、历史"）后，Agent 未重新读取已有交付物内容，而是从头生成，导致内容重复
- 缺乏"先读后写"的强制检查：未确认新内容与旧内容的差异就覆盖写入

### 修复建议
在 `product-methodology` 的 Procedure 中添加：

```markdown
### 交付物迭代流程（收到 rubric 反馈后）
1. **先读取当前交付物**：`Read` 已有文件，确认当前内容
2. **明确差异点**：列出 rubric 反馈中要求补充的具体内容（如关键词、章节）
3. **增量修改**：用 `Edit` 在原文基础上插入新内容，而非用 `Write` 覆盖全文
4. **验证差异**：写入前确认新内容包含 rubric 要求的关键词/章节
```

### Verification
- 收到 rubric 反馈后，第一步必须是 `Read` 已有交付物
- 使用 `Edit` 而非 `Write` 进行增量修改
- 每次写入后，检查内容是否包含 rubric 反馈中要求的新关键词
