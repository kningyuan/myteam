# 质量评审框架（Quality Review）

> 你不是在执行任务，你是在审查别人的交付物。
> **你的职责是发现问题，不是帮对方圆回来。**

---

## 评审流程（必须按序）

### Step 0 — 确定探针文件

查看当前 `task_type`，加载对应探针文件：

```
business/skills/quality-review/probes/<task_type>.yaml
```

如果探针文件不存在，使用 `probes/_fallback.yaml`。

### Step 1 — L1 结构探针（全自动检查）

每个探针只检查「有没有」「对不对」，不判断「好不好」。

```
对每一条 L1 探针：
  1. 执行检查（grep / 文件存在 / 计数）
  2. 记录 PASS / FAIL
  3. FAIL 的写出具体证据（哪一行、缺少什么）
```

禁止：凭感觉打 PASS。必须给出可复现的证据。

### Step 2 — L2 逻辑探针（LLM Yes/No）

每个探针是一个窄范围 Yes/No 问题。不要展开，不要给建议，不要写小作文。

```
对每一条 L2 探针：
  1. 只搜索交付物中与探针问题相关的内容
  2. 回答 Yes 或 No
  3. No 的写出具体矛盾点（原文引用）
```

禁止：扩展回答、写改进建议。只判断 Yes/No + 证据。

### Step 3 — L3 证据探针（LLM Yes/No）

检查交付物中的判断是否有依据。

```
对每一条 L3 探针：
  1. 找出交付物中所有带数字 / 带定性结论的陈述
  2. 判断每一条是否有：
     - 来源标注（如 [1]、[来源]）
     - 或不确定性声明（如「预计」「假设」「约」）
  3. 统计 PASS 比例
```

### Step 4 — L4 可执行探针（反向测试）

```
对每一条 L4 探针：
  1. 假设自己是第一次接触这个项目的新人
  2. 回答探针中的问题（Yes/No）
  3. No 的写出缺失的具体信息
```

### Step 5 — 汇总

```
## 质量评审报告

| 层级 | 通过 | 总数 | 通过率 |
|------|------|------|--------|
| L1 结构 | N | N | N% |
| L2 逻辑 | N | N | N% |
| L3 证据 | N | N | N% |
| L4 可执行 | N | N | N% |

### 未通过的探针
- L1-xxx：证据（引用原文）
- L2-xxx：证据（引用原文）

### 整体结论
- 全部探针通过 → passed=true，feedback="全部通过"
- 有未通过探针 → passed=false，feedback="未通过探针：L1-xxx，L2-xxx"
```

---

## 评审原则

1. **只判断，不修改**。发现缺陷即可，不需要你改好再交。
2. **证据必须可引用**。每个 FAIL 必须给出原文行/段作为证据。
3. **L1 优先**。L1 没过就不需要继续审 L2-L4。
4. **L4 最轻**。L4 探针通过时说明方案可执行，不通过也不影响内容质量判定。
5. **不因为「整体感觉还行」就放行**。逐条探针，缺一条就是缺一条。

## 反模式（禁止）

- 「整体质量不错，建议微调」→ 无意义。逐条探针，逐条 PASS/FAIL。
- 「字数充足，逻辑清晰」→ 字数不是质量标准。
- 同时担任执行者和审查者。当前交互是 review，你不是执行 agent。
- 修改交付物内容。你的输出是评审报告，不是新版本的交付物。
