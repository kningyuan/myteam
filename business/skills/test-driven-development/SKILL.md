# 测试驱动开发 (TDD)

> 来源：obra/superpowers (MIT)，适配 myteam。

## 铁律

```
没有先写失败测试，就不写生产代码
```

先写了代码再补测试？删掉，从头来。不要留作"参考"，不要"适配"——删掉就是删掉。

## Red-Green-Refactor 循环

### RED — 写失败测试
写一个最小测试，展示期望行为。要求：
- 只测一个行为
- 名称清晰描述行为（禁止 test1/test2）
- 用真实代码，非必要不 mock

### 验证 RED — 必须看它失败
```bash
npm test path/to/test.test.ts   # 或 pytest path/to/test.py
```
确认：测试**失败**（不是报错）、失败信息符合预期、因功能缺失而失败（非笔误）。
测试直接通过？说明在测已有行为，修正测试。

### GREEN — 最小实现
写最简单的代码让测试通过。不加班能、不重构、不"改进"超出测试范围的部分。

### 验证 GREEN — 必须看它通过
```bash
npm test path/to/test.test.ts
```
确认：测试通过、其他测试仍通过、输出无 error/warning。

### REFACTOR — 清理
仅在 GREEN 后：消除重复、改善命名、提取辅助函数。保持测试绿色，不加新行为。

## 完成前验证清单

- [ ] 每个新函数/方法都有测试
- [ ] 实现前看到了每个测试失败
- [ ] 每个测试因预期原因失败（功能缺失，非笔误）
- [ ] 写了最小代码使测试通过
- [ ] 所有测试通过
- [ ] 输出无 error/warning
- [ ] 测试用真实代码（非必要不用 mock）
- [ ] 覆盖了边界和错误场景

## myteam 红线

- 执行前必须 Read 本 SKILL.md 全文
- Bug 修复必须先写复现测试（failing test），再修复
- 禁止"先实现再补测试"——测试通过不能证明任何事
- Gate 验收时，`测试结果`章节须含可复现的测试命令与输出
