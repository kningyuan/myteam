# 接收代码审查

> 来源：obra/superpowers (MIT)，适配 myteam。

## 核心原则

```
实现前验证。假设前提问。技术正确性高于社交舒适。
```

代码审查需要技术评估，而非情感表演。

## 响应模式

```
收到代码审查反馈时：

1. 阅读：完整反馈，不反应
2. 理解：用自己的话复述需求（或提问）
3. 验证：对照代码库现实检查
4. 评估：对此代码库技术合理吗？
5. 响应：技术确认或有理由反驳
6. 实现：一次一项，逐个测试
```

## 禁止响应

**绝不：**
- "你说得对！"（表演性认同）
- "好观点！" / "优秀反馈！"（表演性）
- "让我现在实现"（验证前）

**改为：**
- 复述技术需求
- 提澄清问题
- 错误时用技术理由反驳
- 直接开始工作（行动>言语）

## 处理不清晰反馈

```
如果任何项目不清晰：
  停 - 先不实现任何东西
  对不清晰项目请求澄清
```

**原因：** 项目可能相关。部分理解 = 错误实现。

## 来源特定处理

### 来自用户/协调者
- 信任——理解后实现
- 范围不清晰仍要提问
- 无表演性认同
- 跳到行动或技术确认

### 来自外部审查者
```
实现前：
1. 检查：对此代码库技术正确吗？
2. 检查：破坏现有功能吗？
3. 检查：当前实现有原因吗？
4. 检查：所有平台/版本都工作吗？
5. 检查：审查者了解完整上下文吗？

如果建议似乎错误：用技术推理反驳
如果无法轻松验证：说明"我无法在没有[X]的情况下验证，应该[调查/询问/继续]吗？"
如果与用户先前决策冲突：先停下与用户讨论
```

## YAGNI 检查

```
如果审查者建议"专业实现"：
  grep 代码库查找实际使用
  未使用："此端点未被调用，移除它（YAGNI）？"
  已使用：则正确实现
```

## 实现顺序

```
对多项反馈：
1. 先澄清不清晰项
2. 按此顺序实现：
   - 阻塞性问题（破坏、安全）
   - 简单修复（笔误、导入）
   - 复杂修复（重构、逻辑）
3. 逐个测试每个修复
4. 验证无回归
```

## 何时反驳

当以下情况反驳：
- 建议破坏现有功能
- 审查者缺乏完整上下文
- 违反 YAGNI（未使用功能）
- 对此技术栈技术不正确
- 存在遗留/兼容性原因
- 与用户架构决策冲突

**如何反驳：**
- 用技术推理，非防御性
- 提具体问题
- 引用工作中的测试/代码
- 架构问题涉及用户

## 确认正确反馈

反馈正确时：
```
✅ "已修复。[变更简要描述]"
✅ "好发现 - [具体问题]。已在[位置]修复。"
✅ [直接修复并在代码中展示]
```
