# 团队偏好库

## engineering

- 代码注释、docstring、commit message 统一用中文
- 最小 diff 原则：只改任务要求的代码，不顺手重构
- 改动前先理解现有契约（函数签名、API、数据模型），破坏性改动先更新契约
- 新增逻辑必须有对应测试，测试金字塔：单元 > 集成 > E2E
- 禁止硬编码环境配置（路径、密钥、端口），用配置文件或环境变量
- 交付前自检：编译通过、测试通过、无调试残留、diff 只含任务相关改动

## product

- 问题空间优先：先理解用户痛点，再想解决方案
- 需求必须有可验证的验收标准（不是"用户满意"，而是可执行断言）
- 竞品功能不等于需求，需验证是否解决真实痛点
- MVP 只验证一个核心假设，砍掉所有不服务该假设的功能
- 优先级排序：按"价值/成本"比，而非按"谁提的"

## communication

- 所有输出用中文（代码标识符除外）
- 汇报用结构化格式：结论先行 → 关键发现 → 证据 → 下一步
- 交付物用 Markdown，标题层级清晰（# → ## → ###）
- 长文档加目录和章节摘要
- 技术术语保留英文原文（如 API、SSE、DAG），不强行翻译

## collaboration

- 任务间通过契约模型传递，不用口头描述
- coordinator 不执行 worker 任务，只做分解、仲裁、汇总
- 每个 Gate 失败必须记录原因和修复方案
- 任务交接时附加上下文（前置交付物路径、约束、验收标准）
- 冲突由 coordinator 仲裁并记录 ADR（Architecture Decision Record）
